# Eulerase v0.1: presenter and window Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give Eulerase its window: every decision the window makes lives in a presenter that is tested without a display, the window is a thin Tk shell over it, and the command starts it. The window shows the graph, the step-through, the five tables and the k-mer spectrum, and it repairs the window findings of the spec.

**Architecture:** `eulerase.gui.presenter` holds the state and every decision and imports neither Tk nor matplotlib; it talks to a view, a worker and a scheduler through three protocols frozen below, so it is tested with fakes. `eulerase.gui.app` implements the view with Tk widgets, a worker thread and a polled queue, and nothing else. Two drawing pieces that a test can reach without a display, the step-by-step scene and the spectrum chart, live in `eulerase.render` with the redrawn figure and the reading-order layout.

**Tech Stack:** Python 3.13, tkinter (standard library), matplotlib's Tk backend, the first plan's core; pytest and ruff.

**Spec:** `docs/superpowers/specs/2026-11-09-eulerase-v0.1-design.md` (the authority; where this plan and the spec disagree, the spec wins). This plan covers spec section 12 steps 5 and 6 and the hands-on pass of step 8. Spec sections 6.3 and 7, as the owner approved the window design (the palette, the reading-order layout, the redrawn figure), replace the first plan's palette constants and its `compute_layout`; "render additions" in Frozen interfaces freezes what replaces them. The first plan (`docs/superpowers/plans/2026-11-09-eulerase-v0.1-core.md`, task ids `A` to `AD`) delivers the core this plan stands on; its Frozen interfaces are the contract (see "Depends on the first plan"). The opening plan (`docs/superpowers/plans/2026-11-11-eulerase-opening.md`, ids `RA` to `RH`) has code tasks (`RA` to `RE`) that run beside this one and serial tasks (README and AGENTS) that run after it.

## Global Constraints

- **The spec is the authority.** A task that cannot be done as the spec says returns NEEDS_CONTEXT; it does not improvise. Parked and dropped features (spec section 3) are not built, however easy: no error model, no binning, no reference comparison, no molecular weight, no outlier flag, no genotype or clinical view, no comparison tab.
- **No real root, no main loop in a test.** No test may create a real Tk root or enter a main loop; the suite's `tests/conftest.py` makes any attempt fail at once (it replaces `tkinter.Tk` and `tkinter.Toplevel` with subclasses of the real classes whose `__init__` raises `AssertionError` before the parent runs, and each subclass carries the class attribute `eulerase_window_guard = True`; it does so at module level, when pytest imports it, before any test module is collected, and an autouse fixture installs them again before each test); a test that starts a child interpreter and imports anything under `eulerase.gui` makes the child apply the same guard first (the frozen preamble of Frozen interfaces); a test that would is a defect. **Marker first.** Any code, in a test or in a child interpreter, that is about to call `tkinter.Tk`, `tkinter.Toplevel` or anything that could reach them first checks `getattr(tkinter.Tk, "eulerase_window_guard", False)` and the same for `Toplevel`, and stops with a failure, without calling, if a marker is absent (in a child interpreter the stop is `raise SystemExit(3)` with a one-line message, and the parent test fails on exit status 3 as "the guard was not installed"). No check of the guard may be one that opens a window if the guard is wrong. Because the guard is installed at collection, a test module may import `eulerase.gui.app` at module level safely; `app.py` never creates a root at import. The machine's owner must never have a window opened by a test, and a test must never hang in a main loop (see the safety rule of Frozen interfaces).
- **Independence.** Nothing is imported from any other project and nothing is copied about genotype files, variant identifiers or clinical reports. The window code is carried from the explorer half of `$EULERASE_SOURCE/gui.py` only (that file also holds a genotype half, which is never carried). The window adds no dependency: `tkinter` is the standard library and matplotlib's Tk backend ships with matplotlib.
- **Never open a window.** No task and no test calls a real `tk.Tk()`, starts the window or runs the source's window (the guard's proving test calls the guard's raising replacement, after checking it is in place). The hands-on pass is the controller's, run only if the owner has allowed it (see "Hands-on pass (controller)"). A behaviour that no display-free test can reach is stated in its task as a hands-on item; no test is written to fake it.
- **Public repository.** No tracked file, test or commit message holds a user-folder path, a drive-letter path, a personal name other than the licence holder, an email address, or a path into any workspace. The source is named only as `$EULERASE_SOURCE`. Gate lines are relative to the repository root.
- **Structure (spec 5).** `eulerase.gui.presenter` imports the standard library, `eulerase.analysis`, `eulerase.errors`, `eulerase.io`, `eulerase.kmers` and `eulerase.sequence`, and imports none of `tkinter`, `matplotlib`, `eulerase.render` or `eulerase.gui.app`. `eulerase.gui.app` imports the presenter, `eulerase.errors` and `eulerase.render` and implements the view protocol and nothing else. `src/eulerase/gui/__init__.py` has no import and no statement but a docstring. The only modules under `src/eulerase/gui/` are `__init__.py`, `presenter.py` and `app.py`: spec 5 names no other, so work inside one file is sliced into waves.
- **The presenter decides, the window shows.** A rule a presenter test could cover never lives in `app.py`. The presenter is built and tested first with fakes (a fake view, a fake scheduler, a fake worker); a presenter test is written before the code it guards.
- **Tests (spec 8.1).** Each test names the behaviour it guards and fails if that behaviour breaks; it checks against an independent answer (a brute-force count, a direct call of the core, a value computed in the test), never the code against itself. One test per behaviour; near-duplicates are one parametrized test; no test pins wording or a constant. No test needs a display, the network or the home directory, and no test constructs a real `tk.Tk()` (the guard's proving test calls the raising replacement and nothing else does). Owner, 2026-11-11: "Same princples regarding the lean test suite, but keep in mind a failing green is worse than a red." Where a check is a history of calls or a position on a figure, one `test_oracle_rejects_*` in the same file shows the check fails on a deliberately wrong history or figure. A test that needs `tkinter` to import the window uses `pytest.importorskip("tkinter")` with a stated reason, and the task's report says whether it ran or skipped.
- **Task cycle (every task).** Write the tests first, run them and see them fail for the reason the task states, implement the smallest change, run them green, run `python -m ruff check` on the touched files, commit. The report quotes each command and the last lines of its output and lists separately what was not run. A `Mode: code` task runs only the test files it touches and the test files that import a module it changes (`git grep -l "eulerase.gui\|eulerase.render" tests/`), never the three gates; the nested gate-runner and the landing run them. Every task that edits a file under `src/eulerase/gui/` also runs `tests/test_gui_source_rules.py` once WA has landed.
- **Words and text (spec 5.1, 7).** Window text, status messages and chart text say "multiplicity" or "times seen"; none holds "coverage", "cov=", "depth" or "bubble". No string in `src/eulerase/gui/` holds a character outside the Basic Multilingual Plane. Labels are sentence case. A multiplicity is never presented as read depth, copy number or evidence of anything in an organism. The minimum-multiplicity and tip-clipping controls carry the help text of spec 5.1 and row A2: they act as error filters only when the input is a set of reads; on a single assembled sequence a low count marks a rarer k-mer, not an error; tip clipping can remove the true end of a sequence.
- **Palette once.** The palette is the constants of `eulerase.render` (spec 7, Palette; frozen under "render additions" below). No colour literal appears in `src/eulerase/gui/`. There is one theme: no dark mode, no second set of styles, and nothing planned for one (owner, 2026-11-24).
- **Threads (spec 7).** Only the window's own thread touches a widget. A build runs in a worker thread and returns its result through a queue the window polls.
- **Ids in text.** A test may name a finding of spec section 4 (`D5`, `G1`). No file, commit message or comment names a task id of any plan.
- **Commits.** `type(scope): summary` as each task names. One concern each. The body explains, for a developer reading `git log`, the problem with a concrete case, the change, why this design and which tests pin it. No task or review ids, no brief or untracked file cited, no attribution trailer. Stage files by name; never `git add -A`; never amend, rebase, reset, stash, push or `--no-verify`. Wrap at 72.
- **Shell.** Never `sed -i`. A denied tool call is reported, never retried another way. Bound every command with a timeout; a test that can hang is a defect, so a test that starts a thread waits with a timeout. Scratch files go in a `mktemp -d` directory outside the repository.
- **Shared files.** No task of this plan edits `README.md`, `AGENTS.md`, `pyproject.toml`, `LICENSE` or `.gitignore`, with one exception: WA replaces an explicit package list in `pyproject.toml` with setuptools' discovery, only if it finds one (it should not: the first plan freezes discovery). A task that finds it needs any other edit of a shared file returns NEEDS_CONTEXT.
- **Unclear is not a stop** (spec 12.1). An unclear instruction is resolved from the spec section the task cites and the reading taken is recorded in the report. A task returns NEEDS_CONTEXT only for a real contradiction between two rules, or where a choice would change a number, a label or a file format that a user sees.

## Frozen interfaces

Everything two tasks must agree on. Dataclasses are `@dataclass(frozen=True)`; sequences inside them are tuples. Names of the first plan are used as it freezes them.

**Modules.** `src/eulerase/gui/__init__.py` (docstring only), `src/eulerase/gui/presenter.py`, `src/eulerase/gui/app.py`. Changed or added in `eulerase.render`: the colours, `compute_layout`, `legend_entries`, `draw_figure`, `StepScene` and `draw_spectrum` (below). Imports as in Global Constraints.

**Shapes** (`presenter.py`).
- `FormValues(text: str, input_mode: str, k_text: str, both_strands: bool, unique: bool, min_multiplicity_text: str, clip_tips: bool)`. `input_mode` is `"sequences"` or `"kmers"`. `k_text` and `min_multiplicity_text` are exactly what the user typed; an empty minimum means none.
- `TableView(name: str, columns: tuple[str, ...], rows: tuple[tuple[str, ...], ...], note: str | None)`. `columns` and `rows` come from `analysis.columns(name)` and `analysis.rows(...)` cut by `analysis.limit_rows`; `note` is that function's note; for `Contigs` the note also holds the `orf rule: <value>` line that `result_view` puts in `details` (the same value; spec B7 states the start codon rule wherever ORFs are shown), after the cut note if there is one. For `Assembly` the table holds only the numeric rows (`contigs` to `clipped k-mers`); its two text rows (`settings`, `orf rule`) go to `ResultView.details`.
- `ResultView(analysis: Analysis, layout: object, headline: str, status: str, details: tuple[str, ...], tables: tuple[TableView, ...], steps: int)`. `layout` is whatever the injected layout function returned, opaque to the presenter; `headline` is `analysis.headline`; `status` is one line holding the headline and `analysis.settings_text`; `details` are the lines of the Assembly tab: `settings: <settings_text>`, `orf rule: <value>`, then every note of the analysis; `tables` are in `analysis.TABLES` order; `steps` is the number of steps over all trails.
- `BuildOutcome(token: int, analysis: Analysis | None, layout: object, error: str | None)`: exactly one of `analysis` and `error` is not `None`.
- `Example(name: str, text: str, input_mode: str, k: int, both_strands: bool, unique: bool, min_multiplicity: int | None, clip_tips: bool)` and `EXAMPLES: tuple[Example, ...]` (the table below).
- Constants: phases `EMPTY = "empty"`, `BUSY = "busy"`, `READY = "ready"`; `EXPORT_KINDS = ("figure", "csv", "fasta", "genbank", "gfa")`; `CONFIRM_ABOVE_KMERS = 100_000` (patchable by tests); `PLAY_INTERVAL_MS = 550`; `DEFAULT_WINDOW = (1280, 640)`, `MIN_WINDOW = (900, 560)`, `SCREEN_ALLOWANCE = (0, 120)` (the height taken by the title bar, the menu bar, the borders and the task bar: Tk's geometry counts the client area only).

**Pure functions** (`presenter.py`).
- `table_views(a: Analysis) -> tuple[TableView, ...]` and `result_view(a: Analysis, layout: object) -> ResultView`.
- `records_to_text(records: Sequence[Record]) -> str`: `>name` then the sequence, one pair per record, joined by `\n`; `sequence.parse_records` reads it back to the same sequences and names.
- `estimate_kmers(records: Sequence[Record], k: int | None, *, both_strands: bool, input_mode: str) -> int`: the number of k-mers a build would generate, counted as spec 6.4 counts them (before any duplicate is dropped, both strands included): `sum(max(0, len - k + 1))` over the records for `"sequences"`, one per record for `"kmers"`, doubled with both strands.
- `fit_window(screen_width: int, screen_height: int) -> tuple[int, int]`: `DEFAULT_WINDOW` reduced to fit the screen less `SCREEN_ALLOWANCE`, never below `MIN_WINDOW` (the minimum wins on a screen too small for it).

**Protocols** (`presenter.py`, `typing.Protocol`).
- `View`: `read_form() -> FormValues`; `canvas_aspect() -> float` (the graph canvas's width over its height, read on the window's thread after `update_idletasks()`, and `FIGURE_ASPECT` when the width or the height is under 2 pixels, as on a canvas not yet mapped); `set_form(form: FormValues) -> None` (puts the values in the controls, builds nothing); `set_k_enabled(enabled: bool) -> None`; `show_status(message: str, error: bool = False) -> None`; `show_busy(busy: bool) -> None`; `show_result(result: ResultView) -> None`; `clear_result() -> None`; `show_step(step: int, total: int) -> None` (the first `step` steps of the walk are traversed); `set_playing(playing: bool) -> None`; `set_exports_enabled(enabled: Mapping[str, bool]) -> None` (keys `EXPORT_KINDS`); `confirm(message: str) -> bool`; `ask_open_path() -> str | None`; `ask_save_path(kind: str, suggested: str) -> str | None`; `confirm_export(paths: Sequence[str], existing: Sequence[str]) -> bool`; `save_figure(analysis: Analysis, path: str) -> None` (may raise `EuleraseError` or `OSError`); `close() -> None` (ends the window: the one way the presenter closes it).
- `Worker`: `start(job: Callable[[], BuildOutcome]) -> None`: runs the job off the window's thread; its returned outcome is later passed to `Presenter.on_build_outcome` on the window's thread.
- `Scheduler`: `after(delay_ms: int, callback: Callable[[], None]) -> object`; `cancel(handle: object) -> None`.

**Presenter** (`presenter.py`). `Presenter(view: View, worker: Worker, scheduler: Scheduler, *, layout: Callable[[Analysis, float], object] | None = None)`; `layout` defaults to a function returning `None`; the window passes `render.compute_layout`, so the first layout, for the canvas's aspect at the time of the build, is computed in the worker, off the window's thread, and the presenter never imports `render`. A resize is the window's alone (WN): it calls `render.compute_layout` itself, on its own thread, and the presenter is not involved; the same goes for the window's check, when it shows a result, that the layout was made for the canvas's shape as it is by then (WN). Read-only properties `phase`, `analysis`, `step`, `total`, `playing`. Methods, with the task that adds each: `mode_changed(input_mode)`, `build()`, `stop()`, `on_build_outcome(outcome)` (WC); `load_example(name)`, `open_with(form: FormValues | None)` (`None` loads the first example), (WF); `set_step(n)`, `step_back()`, `step_forward()`, `step_start()`, `step_end()`, `play()`, `pause()`, `toggle_play()`, `row_selected(table: str, index: int)`, `shutdown()`, `quit()` (WI); `open_file()`, `load_file(path)`, `export(kind)` (WK).

Rules the methods follow:
- **Phases.** `EMPTY` at construction, after a failed build and after a stopped build; `BUSY` while a build runs; `READY` when a result is shown. Nothing from an earlier build is on screen or exportable in `EMPTY` or `BUSY`.
- **`build()`**, in this order: (1) `form = view.read_form()` and `aspect = view.canvas_aspect()`, both read on the window's thread; (2) settings from the form: in `"sequences"` mode `k_text` is stripped and read as an integer, then checked by `kmers.validate_k`; in `"kmers"` mode `k_text` is never read and `Settings.k` is `None`; an empty minimum is `None`, otherwise it is read as an integer (the core refuses a value below 1); (3) records from `sequence.parse_records` or `sequence.parse_kmer_list`; (4) the confirmation (WM): nothing has changed yet, so a no leaves a playing walk playing; (5) pause the walk and cancel its timer (WI); (6) abandon any running build (the token advances), clear the result, `EMPTY` to `BUSY`, `view.show_busy(True)`, `worker.start(job)`. A failure in (2) or (3) is a failed build: `_fail(message)` pauses the walk and cancels its timer (WI), sets `EMPTY`, clears the result (`view.clear_result()`, `view.set_exports_enabled` all false, `view.show_busy(False)`), and shows the message as an error.
- **The job** runs `analysis.analyze(records, settings)` then the injected `layout(analysis, aspect)`, with the aspect read in step (1); `EuleraseError` becomes `BuildOutcome.error = str(error)`; any other `Exception` becomes one sentence naming the exception type and saying it is a bug in Eulerase, so the busy state always ends.
- **`on_build_outcome(outcome)`**: an outcome whose token is not the current one, or that arrives outside `BUSY`, is discarded without touching the view. An error is a failed build. A success sets `READY`, `step = total`, and shows the result (`show_result`, `show_step(total, total)`, `show_busy(False)`, `set_playing(False)`, `set_exports_enabled`, `show_status(result.status)`); the contig exports (`fasta`, `genbank`, `gfa`) are enabled only when the analysis has contigs.
- **`stop()`** in `BUSY` advances the token, sets `EMPTY`, shows the busy state off and the status "stopped"; in any other phase it does nothing.
- **`mode_changed(input_mode)`**: `view.set_k_enabled(input_mode == "sequences")`. `load_example(name)`, `open_with(form)` and `load_file(path)` call `mode_changed` with the mode they have just put on screen (`"sequences"` for `load_file`) right after their `view.set_form`, so the k box always matches the mode (D7).
- **Closing.** `shutdown()` cancels the pending tick, if any. `quit()` does what `shutdown()` does and then calls `view.close()`, once.
- **Stepping.** `step` runs from 0 to `total`; `set_step(n)` clamps, does nothing when `n` equals the current step, and otherwise calls `view.show_step(step, total)`. Stepping never asks for an analysis or a layout. `play()` cancels any pending tick before it schedules the next, so at most one tick is ever pending; at the end `play()` restarts from step 0. `row_selected("Edges", index)` reads the `global step` cell of that row of the `Edges` table view by header name and sets that step; for the other tables it does nothing.
- **Exports.** `export(kind)` does nothing, and asks no dialog, unless the phase is `READY` and the kind is enabled. `fasta`, `genbank`, `gfa` write `io.fasta_text`, `io.genbank_text`, `io.gfa_text` with `io.write_text_file` to the path `view.ask_save_path` returns (suggested `contigs.fasta`, `contigs.gbk`, `assembly.gfa`); `figure` calls `view.save_figure` (suggested `eulerase.png`); `csv` takes the path as a prefix (a trailing `.csv` is dropped), computes the five files of `io.csv_paths`, calls `view.confirm_export(paths, existing)` every time (`existing` are the paths that already exist) and writes all five tables with `io.csv_text` only if it returns true. An `EuleraseError` or `OSError` is one sentence in the status, as an error.
- **Loading.** `open_file()` asks `view.ask_open_path()`; `load_file(path)` reads `io.read_records` (never shortened), puts `records_to_text(records)` in the input box in `"sequences"` mode (other controls unchanged) and builds. Whatever is loaded is in the input box: that is where a loaded file lives.
- **Confirmation.** When the estimate is above `CONFIRM_ABOVE_KMERS` and not above `kmers.MAX_KMERS`, `view.confirm(...)` is asked, once, before anything changes; a no leaves the screen, the phase and any running build exactly as they were and says so in the status. Above `MAX_KMERS` nothing is asked: the core refuses, and that is a failed build.

Trail t, counted from 1, takes the colour `TRAIL_COLORS[(t - 1) % 3]` and the dash `TRAIL_DASHES[((t - 1) // 3) % 3]`, so no two of the first nine trails share both. Lemon marks the primary action and the walk's current position, and nothing else. - `compute_layout(a: Analysis, aspect: float = FIGURE_ASPECT) -> dict[str, tuple[float, float]] | None`: the reading-order layout of spec 6.3 (row A4).
  - Nodes are taken in the order the walk first meets them: trails in order, in each the source of the first step and then the target of every step, a node already met skipped. They are set on a back-and-forth grid, left to right on one row and right to left on the next, that fills a plot area `aspect` wide and 1 high.
  - With `n` nodes, `c` columns and `r = ceil(n / c)` rows, the node spacing is `min(aspect / c, 1 / r)`. The grid has the `c` from 1 to `n` with the widest spacing, the smaller `c` on a tie.
  - Node `i` is in row `i // c`, and in column `i % c` on an even row and `c - 1 - i % c` on an odd one, at `x = (column + 0.5) * aspect / c` and `y = 1 - (row + 0.5) / r`.
  - It uses no iteration over a solution and no random number: the coordinates depend only on the input and `aspect`, and are the same across runs, hash seeds and platforms.
  - It returns `None` above either count of the drawing limit (`MAX_DRAW_NODES`, `MAX_DRAW_EDGES`), as now, and `{}` for no nodes. An `aspect` that is not finite or is at or below 0 raises `ValueError`, before anything else is read.
- `LegendEntry(label: str, color: str, dash: object, kind: str)` (a frozen dataclass; `kind` is `"trail"`, `"start"` or `"end"`) and `legend_entries(a: Analysis) -> tuple[LegendEntry, ...]`: one `"trail"` entry for each trail, in order, labelled with the trail's number ("trail 1"), with the colour and dash of the rule above, then one `"start"` entry (a solid ring: `color` is `INK`, `dash` is `TRAIL_DASHES[0]`) and one `"end"` entry (a dashed ring: `INK`, `TRAIL_DASHES[1]`). `draw_figure`'s legend and the window's strip both read it, so they cannot disagree.
- `draw_figure(fig, a, layout, upto=None)` keeps its signature and draws spec 7's Figure.
  - In the plot: one arrow per k-mer and trail, with one mark per copy that is filled when the walk has used that copy, or, above `MAX_COPY_MARKS` copies, one count of the copies used. Arrows used take their trail's colour and dash and are drawn thicker; arrows not yet used are `FUTURE`. The current k-mer has a `LEMON` band under its arrow and a lemon label; the current node is `LEMON` with an `INK` outline, so the cue does not rely on colour. Each trail's start has a ring and its end a dashed ring, each with a word that carries the trail's number (`start 2`, `end 2`).
  - Labels are placed by a rule that uses character counts in DejaVu Sans Mono (shipped with matplotlib) and no font metrics: each goes to the first free spot along its arrow, in the order of the walk, touches no node and no other label, is shortened and then left out when it does not fit, and is never moved by a step. A label's text is its k-mer: an arrow can stand for several copies, so no step number is written (the Edges table gives every step).
  - Above `OVERVIEW_ABOVE_NODES` nodes the plot is an overview: dots, one arrow per pair of nodes (a source and a target), and no text. With `layout is None` the plot holds the one explanation of the drawing limit, with both counts.
  - Outside the plot and inside the figure: the headline, the legend (from `legend_entries`), one reading line and the settings line, none touching another text, and, only when either count is above 0, one text that says how many labels were shortened and how many left out. The plot area has the aspect `FIGURE_ASPECT`.
- **Roles.** Every element the figure draws carries a `gid` of the form `role` or `role:key`, so that a test and `StepScene` find it by role and not by type: `node:<letters>`; `arrow:<trail>:<kmer>` (in the overview `arrow:<source>:<target>`); `label:<trail>:<kmer>`; `mark:<trail>:<kmer>` (one per copy); `count:<trail>:<kmer>`; `band:<trail>:<kmer>`; `ring:start:<trail>` and `ring:end:<trail>`; `word:start:<trail>` and `word:end:<trail>`; `note` (the explanation of the drawing limit); `hover` (the read-out of `StepScene.show_hover`, in the scene only); and for the frame `headline`, `reading`, `settings` and `left-out`. The legend is one `matplotlib.legend.Legend`. Trails are counted from 1; a test builds the `gid` it expects and compares, and none parses one.
- `StepScene(fig: Figure, a: Analysis, layout: dict | None)`: draws, once, in one axes filling `fig` (it clears `fig` first), the same plot elements that `draw_figure` draws inside its plot axes. `show(upto: int) -> None` restyles them to the state of `draw_figure`'s plot axes at `upto`, creating no element, moving no label and never calling `compute_layout`. Anything that exists only from some step on (a copy mark's fill, the lemon band and label, the current node's outline, a count) exists from the start and is switched by a property. With `layout is None` the scene shows the same explanation as `draw_figure` and `show` does nothing.
  - The scene draws the plot only. The headline, the legend, the reading line, the settings line and the left-out text are `draw_figure`'s; in the window, Tk draws the headline above the canvas and the legend in the strip under it, from `legend_entries`. WD's comparison covers the plot axes, never the frame.
  - `StepScene.left_out -> tuple[int, int]`: the labels shortened and the labels left out, the counts `draw_figure` writes; the window shows them in its strip when either is above 0.
  - `StepScene.node_at(x: float, y: float) -> str | None`: the node under a point in display pixels, or `None`.

- `draw_spectrum(fig: Figure, a: Analysis) -> None`: clears `fig` and draws one bar per entry of `a.spectrum` (counted over every k-mer before the minimum multiplicity is applied; the drift check confirms it) (x is the multiplicity, height the number of distinct k-mers), axis text "Times seen" and "Distinct k-mers". **The window class, how it reaches the presenter, and the start.** `eulerase.gui.app.Window` is the only name of the window class; it implements `View` (its methods are added by WE, WJ, WL and WN); `app.ThreadWorker` implements `Worker` and `app.TkScheduler` implements `Scheduler` (WO).

In this order: the Tk root and the `Window`, the `ThreadWorker` and `TkScheduler`, the `Presenter` (given the window as its view, the scheduler and the worker, and `layout=render.compute_layout`), then `window.bind(presenter)`, the poll loop, `presenter.open_with(form)` (the first example when `form` is `None`), and the main loop; it returns 0 when the window has closed. - **Safety: the root is reached through the module, and a guard covers every test.** `tests/conftest.py` (WA) holds an autouse fixture that, for every test of the suite, replaces `tkinter.Tk` and `tkinter.Toplevel` with subclasses of the real classes whose `__init__` raises `AssertionError("a test tried to open a window")` before it calls the parent. They are subclasses, not functions, so that modules which subclass them when first imported (`tkinter.simpledialog`, and `tkinter.filedialog` through it) still import inside a test, whatever the order of the tests. **The marker is frozen:** each raising subclass has the class attribute `eulerase_window_guard = True`, and the name is the one every check reads. **Installed at collection:** `tests/conftest.py` also installs the replacements at module level, when pytest imports it, before any test module is collected, so a test module may import `eulerase.gui.app` at module level; the autouse fixture then installs them again before each test (a test may have replaced them with its own fake, and `monkeypatch` restores afterwards). If `tkinter` cannot be imported, the module-level install and the fixture both do nothing. A test that needs a root passes its own fake by replacing `tkinter.Tk` again inside the test, and asserts that it is calling its fake before it calls anything (its own fake is not a guard, so the marker does not apply to it).
- **Safety: a child interpreter guards itself.** A fresh interpreter has no fixture. `tests/window_probe.py` (WA, flat import like `genomes.py`) freezes the child's code once: `GUARD_PREAMBLE`, a string whose statements are `import tkinter`, a subclass of `tkinter.Tk` and one of `tkinter.Toplevel` whose `__init__` raises `AssertionError("a test tried to open a window")`, and the assignment of both to `tkinter.Tk` and `tkinter.Toplevel` (each subclass has `eulerase_window_guard = True`); the preamble is wrapped in `try: import tkinter` / `except ImportError:` so that on an interpreter without `tkinter` it does nothing and the rest of the child runs (there is then nothing to guard); `MARKER_CHECK`, a string of statements which, when `tkinter` is importable, runs `raise SystemExit(3)` with a one-line message unless `getattr(tkinter.Tk, "eulerase_window_guard", False)` and the same for `tkinter.Toplevel` are true; and `child_code(body: str) -> str`, which returns `GUARD_PREAMBLE`, then `MARKER_CHECK`, then `body`, so a child whose guard is missing stops with status 3 before its own imports run. Every test that runs `subprocess.run([sys.executable, "-c", ...])` and imports anything under `eulerase.gui` passes `child_code(body)` and `child_env()`, so a module that built a root at import fails the test with the assertion instead of opening a window, and a parent test treats exit status 3 of its child as "the guard was not installed" and fails. The exceptions are the probes that must see that `tkinter` is never imported (the presenter probe of WA and the command-line probe of WH): the preamble itself imports `tkinter`, so they use `blocked_code(body)` instead, which returns `import sys`, `sys.modules["tkinter"] = None` and `body` (any import of `tkinter` then raises `ImportError`, and no window can open); they read the other names in `sys.modules` as before and count a failed child as a failure.
- **Safety: how `app.py` reaches the root.** `app.py` imports `tkinter` unaliased (`import tkinter`, and `tkinter.ttk` as needed), so `app.tkinter` exists, and `start` creates the root only by calling `tkinter.Tk` through the module (`tkinter.Tk(...)`). It never uses `from tkinter import Tk`, `from tkinter import *`, `import tkinter as tk` or a module-level binding of the root class (`Tk = tkinter.Tk` or an alias of it); the source-rules test of WA refuses the first, second and last, in the files under `src/eulerase/gui/` only. It does not see a default-argument capture (`def f(factory=tkinter.Tk)`), a class attribute, `getattr(tkinter, "Tk")`, `import tkinter as tk` or a file outside that folder; the pre-check below turns the effect of such a form on `start` into a red test, and the rest is the residual risk the review of `app.py` looks for. Every test that calls `start` replaces `tkinter.Tk` with a fake that raises `tkinter.TclError` and, before calling `start`, checks that `app.tkinter.Tk` is that fake; if it is not, the test fails at once and `start` is not called.
- **Safety: the import form in `cli.py` is frozen.** `cli.py` reaches the window only inside the function that starts it, with `from eulerase.gui.app import start`; never at module level and never as `import eulerase.gui.app`. The command-line tests replace it with `monkeypatch.setattr("eulerase.gui.app.start", fake, raising=False)` (the attribute on the real module; `raising=False` because the module exists from WE on but `start` arrives only with WO), not by putting a module in `sys.modules`. After WO lands, these tests replace the real `start`, which is intended. Under the guard above, a mistake in this form is a red test, not a window.
- The close box and File > Quit both call `Presenter.quit()`, which does what `shutdown` does and then calls `view.close()`.
- `app.COMMANDS` is a tuple of `Command(menu: str, label: str, shortcut: str | None, method: str, args: tuple)`; each `method` names a `Presenter` method; there is one command for each of: open file, each of the five exports, build, stop, play and pause (one command, `toggle_play`), step back, step forward, first step, last step, quit (`quit`). ## Hands-on pass (controller)

Run only if the owner has said the window may be opened on this machine. The standing rule is that no window is opened; the controller's ledger records the owner's answer. **If the owner has not allowed it, the pass is skipped, every item below is recorded "not checked", and the run carries on to the opening plan**: the spec requires the pass before the release, not before the private opening. Each item is recorded "checked" with what was seen, or "not checked" with the reason. A scratch directory outside the repository holds any helper script.

1. **Allowed?** Record the owner's answer and the date. If no, stop here and record items 2 to 16 "not checked".
2. **Start.** Run `eulerase` with no arguments from the installed command: a window opens with the first example built. Then `eulerase --gui --seq ACGTACGGA TTGCCATTA -k 4`: the window opens with that input built. Record the screen's pixel size.
3. **Default size** (spec 7 Size, Text, Layout; spec 4 Layout row). Check each: the window fits a 1366x768 screen (say if the screen is another size, and that the 1366x768 claim is then "not checked"); nothing needed is cut off; there is no row of export buttons; the exports are in the File menu with their shortcuts; the sidebar's Examples button posts the Examples menu at the button and each choice loads that example, and its Open file button opens the file dialog; the legend is in the strip under the graph and covers neither the plot nor the headline, for a one-trail and a three-trail example; the status bar is visible and a long error message wraps; every tab title is whole; the minimum-multiplicity and clip-tips controls show their three help sentences (spec row A2: error filters only for reads; a low count on one sequence marks a rarer k-mer; tip clipping can remove the true end); no glyph is drawn as a box; labels are sentence case; the colours are spec 7's palette, and the current position, starts and ends do not rely on colour alone.

## What stays open

- **The executable, its measurements and the release report.** A Windows build (PyInstaller is not installed here), its size and start-up time, `docs/v0.1-report.md`, and the build-time measurement of the first plan's task Y quoted in it, are a later release step (spec 9, 11, 12 step 8). Nothing here builds them.
- **The hands-on items** that were skipped or not checked, recorded in the controller's report.
- **The README's window parts and the screenshot.** The opening plan owns the README. This plan adds no README task and edits no shared file but `pyproject.toml`, and that only in the one case WA describes; the opening plan's code tasks run beside this plan and its serial tasks (README and AGENTS) run after it and describe the window.
- **A step redraw above the target.** If hands-on item 12 records more than 100 ms at the drawing limit, the first remedy is to blit only the restyled artists; it is not built unless the measurement asks for it.
- **The comparison tab** (spec 10). The window leaves room for it as a top-level tab; nothing is built or named for it.
- **A live minimum-multiplicity mark.** The chart marks the setting of the built result; marking the value being typed, before a build, is not built.
- **Disabling "Both strands" on non-DNA input.** The core refuses it with a sentence naming the letters; the window does not grey the box as the user types.
- **Loading a very large file.** The window puts a loaded file in its input box without a size guard; a file of tens of megabytes would make the box slow. The build still refuses an input above the k-mer limit with the core's message. A guard needs a rule the spec does not give.
- **A display for tests.** No test opens a window. A headless display in CI would let the window be built in a test; that is a decision for after the opening.

## What cannot be checked here

- **The window itself.** No task starts a window. The Tk code (`app.py`) is checked by the import probe, the source rules, ruff and a reviewer's reading; its geometry, wrapping, key bindings, responsiveness and drawing time are "not checked" until the hands-on pass. A green gate says the presenter and the drawing helpers behave, not that the window opens.
- **Fonts and extents.** The label, legend, headline and chart checks read extents on the Agg canvas; extents differ a little between fonts and platforms, so each check leaves a margin and compares disjointness, never exact positions. The layout's coordinates use no font and are compared exactly (WB). No Linux result is claimed before CI exists.
- **Skipped window tests.** A test that needs `tkinter` skips where it is absent; the report of each task says whether it ran.
- **The first plan's gaps.** What that plan could not check (CI, Linux, the executable, the `KC` tag, a clean environment) stays unchecked here.
