# Eulerase v0.1: opening the repository Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Write what a reader and a contributor need on the first day (README, CI workflow, release workflow, pull request and issue templates, CONTRIBUTING, changelog, security policy, AGENTS.md), then open the repository, private at first, with the core, the command line and the window in it, watch its first CI run, and check that the package release `v0.1.0` (a tag and a GitHub release holding a source distribution and a wheel) follows from that run.

**Architecture:** Documents, two workflow files, one packaging edit and, before the opening, four small groups of fixes to the code and its tests (tasks RP to RS, from an outside read of the code at `main` 1e8ce89, which holds the window work). The gates workflow runs the gates; the release workflow runs only after a green run of it on `main` and releases the package when the merged version has no tag. The workflows, the templates, CONTRIBUTING and the security policy touch nothing the core or the window touches, so they are written beside the other plans' waves; the `pyproject.toml` fields are one small edit to a file the first plan creates, made after the window plan's first task. README and AGENTS.md are shared files that the first plan's task A creates in a minimal form; they are completed here, one writer at a time, after the window plan's last task has landed, from facts read out of the landed code. The opening itself is done by the controller, never by an implementer, because it pushes.

**Tech Stack:** GitHub Actions, Markdown, `gh`, git, setuptools and `build` (first run by the hosted install step and the release workflow); pytest for the tests of this plan.

**Spec:** `docs/superpowers/specs/2026-11-09-eulerase-v0.1-design.md`, sections 1, 1.1, 1.2, 5, 6.4, 6.6, 7, 8.1, 9, 11, 12 and 12.1 (the authority; where this plan and the spec disagree, the spec wins). Section 9, "Package release" and "Opening the repository", is what this plan carries out. The order of the three plans is: the first plan (`docs/superpowers/plans/2026-11-09-eulerase-v0.1-core.md`, the core and the command line, task ids `A` to `AD`), then the window plan (`docs/superpowers/plans/2026-11-11-eulerase-v0.1-window.md`, the presenter and the window, ids `WA` to `WO`), then this plan's serial task, RF, and the opening. ## Global Constraints

- **The spec is the authority.** A task that cannot be done as the spec says returns NEEDS_CONTEXT; it does not improvise. Parked and dropped features (spec section 3) are not built, described as built, or promised.
- **Two things are called a release; they are kept apart in every document.** "The package release" is the tag `v<version>` and a GitHub release holding a source distribution and a wheel, made by the release workflow; it is part of this plan. "The Windows executable, its measurements and the release report" are a later step, after the package release; they stay out (see "What stays open"). A sentence that says "release" says which one.
- **Only what is shipped.** The opening is the core, the command line and the window, and the package release that the opening's first green run starts. The Windows executable, its measurements and the release report stay out (see "What stays open"). Every document says only what exists at the head it is written for. A document describes the window from the landed code, never from this plan or from memory; no task of this plan opens a window. The README shows a screenshot only if the window plan's hands-on pass produced one (`docs/assets/window.png` is tracked); if that pass was skipped, the README has no image and says in one plain sentence that the window's geometry has not had its hands-on pass. No document says "tested on Linux", "verified" or "supported on Linux" as a result: the workflow is described, a green run is reported by the controller.
- **Independence and the boundary.** Eulerase reads no genotype files, looks up no variant identifiers and interprets nothing for a person (spec 1.1). Documents name no other project except where spec 1.1 does so for the boundary; they do not describe the original explorer or where it lives.
- **Public repository.** No tracked file, commit message or test holds a user-folder path, a drive-letter path, a personal name other than the licence holder, an email address, or a path into any workspace. The source being carried is named only as `$EULERASE_SOURCE`, and only in a plan. This plan is itself a tracked file. The repository is created private and pushed private (owner, 2026-11-24: "Init. open can stay private until I configured rules and looked over a few other things, that would clear Eulerase for now with issues and feat ideas ready for the next v. milestone ready for the roadmap after 0.1.0"); the owner's later switch to public publishes the whole history, so every rule here applies to every tracked file from the first push. The repository's address, `https://github.com/pterw/eulerase` (owner, 2026-11-23: "No problem with gh account name since the repo is planned to be public."), appears in exactly three kinds of place and nowhere else: the `[project.urls]` table of `pyproject.toml` (task RI), the private-report link of `SECURITY.md` (task RJ) and the Gates status badge of the README's badge row (task RF). Two more kinds of absolute address are allowed: the image addresses of the three static badges of that row (task RF) and the SVG namespace (`xmlns`) of the two logo files (task RN). No other absolute address appears in a tracked file, and every other link in every document is relative. Gate lines are relative to the repository root.
- **Three claims kept apart** (spec 1.2): a trail is correct for the graph; a contig is a valid path in the assembly graph built from the k-mers given; a sequence exists in an organism. Eulerase makes the first two and never the third. A contig is not a validated assembly.
- **Multiplicity is not depth** (spec 5.1). Documents say "multiplicity" or "times seen", never "coverage" or "depth", except for simulated reads where the term is correct. The filters (minimum multiplicity, tip clipping) act as error filters only when the input is a set of reads; on a single assembled sequence a low count marks a rarer k-mer, not an error; tip clipping can remove the true end of a sequence. The only two simplifications any document names are those two.
- **Facts come from the landed code.** A document that quotes a help text, a limit, an example or a rule reads it from the tree at its BASE and runs it. It does not copy it from this plan or the spec. Where the landed code and the spec disagree about a fact a document states, the document states what the code does, the report records the difference with both quotations, and the task carries on. It returns NEEDS_CONTEXT only if the difference is a number, a label or a file format that a user sees.
- **Who runs the gates.** A `Mode: code` task of this plan does not run the three gates: it runs only what its change touches (for RA to RE, RG, RI to RL, RN and RO their own checks, since they add no test file; for RH its own test file; for RP to RS the test files they name, each run red and then green by the step that adds the case). The gate-runner runs the gates at landing. The one `Mode: serial` task (RF) runs the commands its document quotes, except the install line, which RF reports as not run (setuptools is not installed here and nothing is installed), and the gate-runner follows.
- **No finding, task or review ids in documents** (README, CONTRIBUTING, AGENTS.md, `CHANGELOG.md`, `SECURITY.md`, templates). Anti-patterns are written in words.
- **No Dependabot and no scheduled run at opening.** Decided: dependencies are pinned exactly, and both are added later only if they earn their keep (see "What stays open"). The one delivery step is the package release workflow (task RK): there is no deployment, no upload to a package index, and no secret beyond the built-in token. The release workflow holds `contents: write`; the gates workflow keeps `contents: read`.
- **Checks that are not tests.** A document is checked by its reviewer against the spec and the landed code, not by a test that pins its wording. The tests of this plan are task RH's, in `tests/test_ci_gates.py`, and the cases that tasks RP to RS add to the existing test files of the code they fix (each guards one behaviour of that code; none pins a document's wording). RH's tests compare the gates workflow with the documented gate commands and with the frozen shape of that workflow (its trigger, permissions, matrix and steps), and fail when they drift. The release workflow has no test: it is held to its frozen text by task RK's `diff` and by its reviewer (see "The release workflow (task RK)" of Frozen interfaces).
- **Commits.** `type(scope): summary` as each task names. One concern each. The body explains, for a developer reading `git log`, what the file is for and why it says what it says. No finding, task or review ids, no brief or untracked file cited, no attribution trailer. Stage files by name; never `git add -A`; never amend, rebase, reset, stash, push or `--no-verify`. Wrap at 72.
- **Shell.** Never `sed -i`. A denied tool call is reported, never retried another way. Bound every command with a timeout. Scratch files go in a `mktemp -d` directory outside the repository.
- **Shared files** (`README.md`, `AGENTS.md`, `pyproject.toml`, `LICENSE`, `.gitignore`): in this plan only tasks RF (README; `Mode: serial`) and RG (AGENTS.md; `Mode: code`), and RI (`pyproject.toml`: the licence field, the build requirement, keywords and classifiers; `Mode: code`) edit them.

**The workflow (task RA).** One file, workflow name `Gates`. Trigger, exactly:

```yaml
on:
  pull_request:
    paths-ignore:
      - docs/**/*.md
      - CONTRIBUTING.md
      - .github/ISSUE_TEMPLATE/*.md
      - .github/PULL_REQUEST_TEMPLATE.md
  push:
    branches: [main]
```

These lines are the **frozen trigger block**: everything from the `on:` line to the line before `permissions:` (which comes next, then an optional `concurrency:`, then `jobs:`), with no comment, blank line or other key inside it. Task RH's test requires the block in the workflow file to equal these lines exactly, after stripping trailing whitespace and line endings; an added, removed or changed trigger line is a flaw.

Documentation-only pull requests skip the gates, and nothing else does. The `paths-ignore` list holds only the four entries above, one per line, unquoted: Markdown files that packaging and the tests never read. They name `.md` files, not whole directories, because a directory pattern would also skip a Python file added under `docs/`, and `python -m ruff check .` lints it; a pull request that adds an image such as `docs/assets/window.png` or any other non-Markdown file under `docs/` therefore runs the gates, which is the safe direction. `README.md` and `LICENSE` are not on it, because a build can read both (a `readme` or licence entry in `pyproject.toml`), so a change to either runs the gates. `AGENTS.md` is not on it (the workflow test reads its gates block), and neither are `src/`, `tests/`, `tools/`, `pyproject.toml` or `.github/workflows/`. GitHub evaluates path filters against a bounded number of changed files, and a skipped pull request is still covered when it reaches `main`, because every push to `main` runs every gate. A pull request that touches any path not on the list runs every gate on both systems, because a workflow skips only when every changed path matches the list; the one exception is a pull request that changes more files than GitHub's filter inspects, which only the push to `main` then covers (a residual risk, named in the final report). `push` to `main` has no path filter: every push to `main` runs every gate. There is no per-module test selection: the suite is small, and a selector that guesses which tests a change reaches is where a false green comes from.

`permissions: contents: read` at the top. One job with id `gates`, `name: gates (${{ matrix.os }})`, `runs-on: ${{ matrix.os }}`, `timeout-minutes: 20`, `strategy.fail-fast: false`, matrix `os: [windows-latest, ubuntu-latest]`. No `defaults:` key and no `shell:` key: each step uses the runner's default shell (PowerShell on Windows, bash on Linux), because the install line and the three gate lines run unchanged under both (the extras are quoted, so neither shell treats `[dev]` as a pattern). Because no `run:` key has an empty value, every `run:` line of the file is a step's command. Steps in order: `actions/checkout` with `persist-credentials: false`; `actions/setup-python` with `python-version: "3.13"`, `cache: pip` and `cache-dependency-path: pyproject.toml` (the repository has no requirements file, so both inputs are needed); then the install and the three gates, each a step with a **single-line** `run:` (no `|` or `>` block, so the lines can be compared). The allowed keys are fixed: a step that has a `run:` has only `name` and `run`, so none has `if`, `continue-on-error`, `working-directory`, `shell`, `env`, `timeout-minutes`, `uses` or `with`; the job has only `name`, `runs-on` (equal to `${{ matrix.os }}`), `strategy` (with `fail-fast` and a `matrix` that holds only `os`, the set `{windows-latest, ubuntu-latest}`, with no `include` or `exclude`), `timeout-minutes` and `steps`, so it has no `continue-on-error` or `if`. The `run:` lines, byte for byte and in this order (the first is the install, not a gate):

```
python -m pip install -e ".[dev]"
python -m pytest -q -p no:cacheprovider
python -m ruff check .
python tools/check_fresh_export.py
```

A `concurrency` group on workflow and ref with `cancel-in-progress: true` is allowed. No `env:` value that hides a difference between the two systems (no forced encoding, no forced backend): a red on one system is a finding. No deployment, release or secret in this workflow: the package release is the separate workflow of task RK, which starts from a green run of this one. Actions are pinned to a full commit SHA with the version in a comment if the implementer can verify the SHA offline from a file in the repository; otherwise to the major tag (`actions/checkout@v4`, `actions/setup-python@v5`), and the report says which and why. A one-line comment in the file (line 2 of the landed file: "There is no CD: nothing is published in v0.1.") said there is no CD; task RK replaces that line, and only that line, with one comment line that is true: this workflow publishes nothing, and `release.yml` releases after a green run of it on `main`. The trigger block, the permissions and the steps of this workflow are untouched by RK, so task RH's test keeps its meaning.

**The release workflow (task RK).** One new file, `.github/workflows/release.yml`. The file is this text, line for line (the one place where the plan holds a file's full content: every line of it is a guard, and the file cannot be run before the opening, so the reviewed text is the only evidence there is):

```yaml
# Releases the package after a green run of the Gates workflow on main.
# It runs no gate itself and uploads nothing to a package index.
name: Release

on:
  workflow_run:
    workflows: [Gates]
    types: [completed]
    branches: [main]
permissions:
  contents: write
concurrency:
  group: release
  cancel-in-progress: false

jobs:
  release:
    name: release
    if: github.event.workflow_run.conclusion == 'success' && github.event.workflow_run.event == 'push'
    runs-on: ubuntu-latest
    timeout-minutes: 15
    env:
      TESTED_SHA: ${{ github.event.workflow_run.head_sha }}
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.workflow_run.head_sha }}
          persist-credentials: false
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
      - name: decide
        id: decide
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          version="$(python -c "import tomllib; print(tomllib.load(open('pyproject.toml', 'rb'))['project']['version'])")"
          tag="v$version"
          status=0
          auth="$(printf 'x-access-token:%s' "$GH_TOKEN" | base64 -w0)"
          echo "::add-mask::$auth"
          git -c "http.extraheader=AUTHORIZATION: basic $auth" ls-remote --exit-code --tags origin "refs/tags/$tag" || status=$?
          case "$status" in
            0) echo "release=no" >> "$GITHUB_OUTPUT" ;;
            2) echo "release=yes" >> "$GITHUB_OUTPUT" ;;
            *) echo "tag lookup failed with status $status" >&2; exit 1 ;;
          esac
          echo "tag=$tag" >> "$GITHUB_OUTPUT"
      - name: build
        if: steps.decide.outputs.release == 'yes'
        run: |
          python -m pip install build==1.6.0
          python -m build
      - name: release
        if: steps.decide.outputs.release == 'yes'
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          TAG: ${{ steps.decide.outputs.tag }}
        run: gh release create "$TAG" dist/* --target "$TESTED_SHA" --title "$TAG" --generate-notes
```

What each guard does, in a sentence: the job's condition lets only a successful run of `Gates` that a push started release anything, so a red or cancelled run, or a pull request's run, releases nothing, and `branches: [main]` limits it to runs on `main`; the checkout `ref` and the release's `--target` are both the commit that run tested, not whatever `main` has moved to; the `decide` step has three outcomes, and only status 2 of `git ls-remote --exit-code` ("no such tag") sets `release=yes`, status 0 sets `release=no` and any other status fails the job, so a network error is never read as "no tag"; the token is given to the `decide` step, for the tag lookup only and masked in the log, and to the `release` step, and the `build` step never holds it; the lookup sends it as a per-command header, so it is written to no file and to no remote's configuration, and the checkout keeps `persist-credentials: false`; the lookup works the same on a private and a public repository; the concurrency group means a running release is never cancelled, and when several wait GitHub may drop an older waiting one; the newest run still decides from the commit it was started for, so a dropped run's version is released only if a later commit still carries it untagged; `build` is pinned to the version installed where the plan was written. A push to `main` that a later push supersedes has its Gates run cancelled (the landed `gates.yml` cancels a run in progress on the same branch) and releases nothing: the version then releases at the later commit if it is still untagged, or not at all if that commit changed the version (`gates.yml` is not changed for this). The workflow uploads nothing to a package index and holds no secret but the built-in token. The file exists on the default branch only after the opening push, so its first run is the run that follows the opening's first green Gates run, at version 0.1.0. No gate command (none of the `run:` values of the Gates block) appears in it: the gates are run by the Gates workflow only.

   - **Run.** From the repository root: `timeout 300 bash "<script>" "<scratch>/names.txt" "<scratch>/identity.txt" "<sha>"`, where `<script>` is the path in the controller's notes and `<sha>` is the full 40-character id that `git rev-parse HEAD` prints, which must be the head the three gates ran on in step 1.
   - **Pass** means the last line is `RESULT: CLEAN`, the exit status is 0, and the `[control]` line and every gate section (`file names`, `blob contents`, `commit messages`, `history binary`, `screenshot chunks`) show `count=0`.
   - `RESULT: NOT RUN` (exit status 3) means the check could not run. It is never treated as a pass. The controller fixes the cause (no `LICENSE` file in that commit, a names file that lacks the holder's exact name, not at the repository root, a shallow history, an identity file that is not one `Name <address>` line) and runs it again; this is not a wait for the owner.
   - `RESULT: HITS` (exit status 1) is a stop: see the end of this step.
   - **Local only.** The section `local only (not pushed)` describes things that are not part of the push (other branches, tags, the reflog, uncommitted changes). It never blocks. The controller reads it and names in the final report anything it lists.
   - **What is printed.** The script prints section names, counts, paths, short ids and rule names, never file content or a matched string. The controller never pastes file content or a matched string into a report or the ledger.
   - **The screenshot.** The one permitted binary file is `docs/assets/window.png`; the script checks its chunk types and fails any other binary file. The controller also looks at the image itself once (a read of the file, never a window) for a visible path, name or address, and says so in the final report. The two logo files are text (SVG), not binary, and the controller looks at each once, rendered, for a visible path, name or address, as it does for the screenshot.
   - **What the script cannot do,** one line each: it does not find the name of a person other than the owner (no command can; the README legitimately names Euler and de Bruijn); it does not find a string assembled at run time; and a version pin with dots after an `@` reads as an address and gives a false stop, which is resolved by reading the path and rule it names and telling the owner, not by weakening the check.
   - **The identities:** the commit identity of this repository is the owner's global git identity, as in the owner's other repositories, so none is printed. The check is that the set has not grown since the plan was written, as a count that prints only a number: `git log --format='%an <%ae>%n%cn <%ce>' | sort -u | wc -l` prints `1` (the count at the commit this plan was written on; measured, not assumed). A larger number means a task committed under another identity: the controller stops and reports the count, never the identities. This is one of the places where the opening waits for the owner.
   - **A hit is an owner wait.** Any private string already committed that is reachable from the commit to be pushed (in the tracked tree, in an earlier version of a file, or in a commit message) cannot be removed by a new commit, because its ancestor is pushed too, and rewriting history is outside this plan. The controller stops, reports the section, path and rule (never the text), and pushes nothing. This is one of the places where the opening waits for the owner.
   - **The identity count passes only at the number above;** the check passes only when the script's pass and that count both hold.
3. **Sweep for leftovers.**
   - `git grep -n -I -E 'TO[D]O|FIXM[E]|XX[X]' -- .` prints nothing.
   - `git grep -n -I 'indow is not buil[t]' -- . ':!docs/superpowers'` prints nothing: the window is built, so the old command line sentence appears in no README, document, source file or test. Only the plans and the spec, which are point-in-time documents, may quote it; a hit anywhere else is a document that denies a thing the code decides, or a task that left the old line behind; fix it by a task.
   - The install line is quoted everywhere a reader copies it: `git grep -n -I -F 'install -e .[dev]' -- . ':!docs/superpowers'` prints nothing (the quoted form `-e ".[dev]"` does not match it).
   - The first plan's task ids in tracked files that are not plans: `git grep -n -I -E '\b[Tt]ask [A-Z][A-Z0-9]*\b' -- . ':!docs/superpowers/plans'` prints nothing.
   - Finding ids in the documents: `git grep -n -E '\b(A[1-8]|B[2679]|D([2-9]|1[02])|G1|R[1-3])\b' -- README.md AGENTS.md CONTRIBUTING.md CHANGELOG.md SECURITY.md .github` prints nothing (read each hit; a word that happens to match is listed, not edited).
   - `git ls-files` lists no file the repository should not hold (no scratch, cache, export or `.env`).
4. **Create the repository and push.** Owner, 2026-11-23: "Vsibility, public on opening so make sure that there is a plan for setting up the repo to be well-constructed, with a proper readme.md and necessary repository files, MIT license unless Apache 2.0 is deemed better, contributing.md, PR-body template, etc." and "Releasee, a tag and gh actions for release from PR merges." And, 2026-11-24: "Init. open can stay private until I configured rules and looked over a few other things, that would clear Eulerase for now with issues and feat ideas ready for the next v. milestone ready for the roadmap after 0.1.0". So the repository is created private and pushed private:
   - `gh repo create eulerase --private --source . --remote origin` (no `--push`).
   - `git rev-parse HEAD` gives `<sha>`; confirm it is the head the gates ran on and the head the privacy check of step 2 reported clean for. Then `git push --atomic origin <sha>:refs/heads/main`.
   - `gh repo view eulerase --json url,visibility` and quote the address and that the visibility is private.
   - **Private vulnerability reporting.** It is not turned on at the opening (GitHub describes it for public repositories). `SECURITY.md` relies on it, so it waits for the owner's switch to public, and the final report lists it (step 7).
5. **Watch the first run.** Before any watcher is dispatched, replace the whole `## CI` section of the controller's constraints file (the one that says "None yet" and forbids a watcher) with this, one `ci` block under a heading that contains `CI`:

   ````
   ## CI

   ```ci
   workflow: Gates
   event: push
   jobs: 2
   blocking:
     - 'gates (*)'
   ```
   ````

   `workflow` is the workflow's `name`; `event` is the event of the run (`push` to `main`; the watcher is given the branch separately); `jobs: 2` is the exact count (`gates (windows-latest)` and `gates (ubuntu-latest)`); the one glob makes both blocking. Nothing is advisory, so there are no other keys. Then dispatch a `ci-watcher` in the background with these fields: `WORKSPACE` (the plan's workspace directory, the one holding that constraints file), `HEAD` (the literal 40-character `<sha>` that was pushed, never `HEAD` or a short SHA, which the watcher refuses), `BRANCH` `main`, `PREFIX` (a log prefix matching `[a-z][a-z0-9-]{0,39}`, for example `open-ci1`; a new one for each loop of step 6), and `REPO` (this repository's root). Wait for its summary and quote each job's result. If it answers `NO_RUN`, poll `gh run list --branch main --workflow Gates --event push --limit 5 --json databaseId,headSha,status,conclusion` every 30 seconds, each call under a timeout, for at most 10 minutes. When a row shows the full `<sha>` as `headSha`, dispatch again with `RUN_ID` set to that row's `databaseId`. If no row shows it after 10 minutes, start no repair loop: check whether Actions is enabled for the repository with `gh api repos/{owner}/{repo}/actions/permissions` (its `enabled` field), also run `gh run list --limit 5` and `gh workflow list`, quote their output, report the run as not created, and stop (a wait for the owner, case 4).
   - **Release check.** A watcher's `ci` block names one workflow and one event, so no watcher is used for the `Release` workflow; the controller checks it with `gh`, every call under a timeout. A red Gates run makes the release job skip: that is the design, and the release follows the repair push of step 6 that goes green. Once the Gates run is green for the pushed SHA (the first push, or the last repair push), poll `gh run list --workflow Release --limit 5 --json databaseId,headSha,status,conclusion,event` every 30 seconds for at most 10 minutes until a row shows that SHA as `headSha` with a `status` of `completed`; then run `gh release view v<version> --json tagName,targetCommitish,assets` and `git ls-remote --tags origin refs/tags/v<version>`, where `<version>` is the `version` of `pyproject.toml` at the pushed commit. Quote each output. **Pass** means: that row's `conclusion` is `success`, the tag exists and points at the pushed SHA, and the release holds exactly two files, one whose name ends `.tar.gz` and one that ends `.whl`. Defaults: no completed `Release` run for the pushed SHA within 10 minutes after the green Gates run is a wait for the owner (case 4); if the version is still untagged then, the release follows the next push to `main`. A completed run whose conclusion is not `success`, or a release that differs from the pass condition, is a wait for the owner (case 6), except as the failed step decides: a run that failed in the `decide` or `build` step created nothing and is a red of class (c) of step 6; a run that failed in the `release` step is a wait for the owner (case 6), whatever `gh release view` shows, because the command makes a draft before it uploads. A release that holds other files is a wait for the owner (case 6) too: a pushed tag is not deleted or moved by the controller, and the workflow cannot retry it, because the tag then exists.
   - **Settings.** After the release check, the controller sets, each by one `gh` command under a timeout, quoted with its output: the description (the `description` of `pyproject.toml`, read with `tomllib`) and the topics `de-bruijn-graph`, `bioinformatics`, `genome-assembly`, `eulerian-path`, `education` and `python` (`gh repo edit --description ... --add-topic ...`, run from the repository root, where `origin` names the repository); issues on and the wiki off (`gh repo edit --enable-issues=true --enable-wiki=false`). A description, topic, issues or wiki command that fails is reported with its output, and the opening carries on. A read of each setting follows (`gh repo view --json description,repositoryTopics,hasIssuesEnabled,hasWikiEnabled`).
   - **Protection of `main` is not set.** It is an owner-gated step: a required check stays pending and blocks merging on a pull request whose workflow was skipped by a path filter, which is every documentation-only pull request here, and it would also stop the controller's repair pushes. The controller reports that it is not set.
6. **If the first run is red.** Linux has never run this code, so a red is expected to be possible. The failing job's log names the failing test or step. Say apart three classes: (a) a red that is the test's fault (it assumed Windows paths, line endings, a locale, a tool that is not on the runner); (b) a red that is the code's fault (the tool behaves differently on Linux); (c) a red that is neither a test nor the code: the workflow file (either one), `pyproject.toml` (the first hosted build can fail on it) or the runner setup (YAML, an input name, the pip cache setting, a missing token scope, a missing tool on the image). Then, in this order: a fresh implementer fixes it in a code phase (for (a) the failing test first, made correct for both systems without being weakened; for (b) the failing test first, the test stays and the code is fixed; for (c) there is no test to write first, so the change is to the workflow file or to `pyproject.toml`, with the failing job's log line quoted as the evidence in its place; a change to `release.yml` is made in the file and in the plan's frozen block together, so the plan stays the reviewed text, and the tests of task RH still pass); a reviewer reads it; the controller lands it, runs the three gates locally, runs Step 2's privacy check (its script, with the new head's full id as the third argument) and Step 3's sweeps again on the new head (the same pass rules: a private string in the repair is a wait for the owner and is not pushed), and pushes by SHA with `git push --atomic origin <new-sha>:refs/heads/main`; a new watcher follows that SHA. At most three such loops, of any class together. After the third red, or when a red is not reproducible or has a cause outside the repository (a runner image, a service), the controller stops and reports what is red and why, without further changes. A red is never made green by skipping or loosening a test or removing a matrix entry.
7. **Final report.** The repository's address; the head SHA; the CI run and its result per job (green, red with the reason, or not finished); the privacy and leftover checks with their output; and everything "not checked": that no tracked file or commit message names a person other than the licence holder (no command searches for that), that no string is split across lines or built at run time (only the reviewer's reading covers it), that the screenshot was looked at once (or that none exists), that a pull request with more changed files than GitHub's path filter inspects was never skipped wrongly, the Windows executable and its measurements and the release report (the later step, not the package release), the hands-on items of the window plan that were skipped or not checked (and whether the README has a screenshot), tests skipped for want of tkinter on a runner, anything Linux showed, any behaviour on a Python other than 3.13, and that the actions are pinned to major tags if RA could not verify a SHA. It also states the package release: the tag, the commit it points at and the two file names (or why there is none); each setting of step 5, with its output; that protection of `main` is not set; and the Actions minutes the first run used on each system (a private repository's runs draw on the account's included compute). It lists what waits for the owner's switch to public: private vulnerability reporting, which `SECURITY.md` relies on, and whether the Gates badge renders for a reader without access (GitHub: "Workflow badges in a private repository are not accessible externally").

**Where the opening may wait for the owner, and nowhere else (six cases).** (1) `gh auth status` fails, lacks the `workflow` scope, or a remote already exists. (2) `gh repo create` fails because the name is taken or the permission is missing; there is no fallback name. (3) A private string already committed, in the tracked tree, in an earlier version of a file or in a commit message, shown by `RESULT: HITS` (step 2, and again before each repair push in step 6). (4) The fix loop's third red, a red with a cause outside the repository (step 6), or no run created for the pushed SHA within 10 minutes (step 5); the same when no completed `Release` run for the pushed SHA shows within 10 minutes after the green Gates run (if the version is still untagged then, the release follows the next push to `main`). (5) The identity count of step 2 above the stated number. (6) The `Release` run completes with a conclusion other than `success`, or the release differs from the pass condition (step 5), except that a run that failed in the `decide` or `build` step created nothing and is a red of class (c) of step 6; a run that failed in the `release` step is a wait for the owner (case 6), whatever `gh release view` shows, because the command makes a draft before it uploads; a pushed tag is not deleted or moved by the controller. Every other case has a default in this plan: a red gate or a tracked change sends the controller back to a fix task, a privacy check that answers `RESULT: NOT RUN` is fixed by removing its cause (for example by rebuilding the names file) and run again, a missing network for the setup check is reported as "setup not run", and an action without a verifiable SHA is pinned to its major tag and reported.

The package release itself (the tag and the GitHub release with a source distribution and a wheel) is not open: the opening carries it out.
- **The window's hands-on items** that the window plan's pass skipped or did not check, and the screenshot if that pass made none. The README says so in one sentence and is amended when the pass is done.
- **Dependabot and a scheduled run.** Decided not to add them at opening (dependencies are pinned exactly). Revisit at the executable step, when the release report records a pinned dependency with a published advisory, or when the owner asks; a scheduled run would also be the first way to notice a change in a runner image. Pinning actions to SHAs goes with the same decision if RA could only use major tags.
- **An output name that holds a character Windows refuses** (`*`, `<`, `?`). It passes the check of every output before any work and fails at the write, after earlier output; no check can list every name a system refuses. A later issue; tasks RP to RS do not change it.
- **Branch protection and required checks.** Not set by this plan; the controller reports that they are not set. It is an owner-gated step: a required check stays pending and blocks merging on a pull request whose workflow was skipped by `paths-ignore`, which is every documentation-only pull request here, and it would also stop the controller's repair pushes. The owner decides how documentation-only pull requests are merged if checks are required later.

## What cannot be checked here

- **A hosted run.** The gates workflow is written and read offline. Its syntax, the runner images and the behaviour on Linux are first shown by the run in Opening step 5. No result for Linux is claimed before it.
- **The pins of the actions.** A SHA cannot be verified without the network; if RA uses major tags, that is reported, not hidden.
- **Document truth beyond the checks.** The README and AGENTS.md are checked by running their commands and by quoting a source for each claim, and by a reviewer. No test pins their wording, so a later change to the code can make a sentence stale; the reviewer of any task that changes a help text, a limit or a rule reads the README for it.
- **The window itself.** The README describes the window from its source and tests; no task here opens one. Its geometry, wrapping and responsiveness are checked only if the window plan's hands-on pass ran.
- **Setup from a clean machine.** RE runs the setup only if a scratch environment can be made without the network.
- **The release workflow on a hosted runner.** Written and read offline, and held to its frozen text by the `diff` of tasks RK and RO at creation and by its reviewer; nothing checks it afterwards but a reader of a later commit's diff. Its `decide` step is run only against a local bare repository (task RK, Step 4). It is first shown by the `Release` run that follows the opening's first green Gates run. The field names it reads, `head_sha` and `event` of the `workflow_run` object, were read in the REST schema of a workflow run, not in an example of the trigger's documentation page; that the event carries that object is an inference the first run confirms. A push to `main` that a later push supersedes has its Gates run cancelled and releases nothing; the version then releases at the later commit if it is still untagged, or not at all if that commit changed the version.
- **A re-run, and an older commit as the release's target.** Whether re-running an earlier Gates run starts `Release`, and for which commit, is not documented; if it does, it releases that run's commit when its version has no tag, and the workflow has no guard against it (a guard on the tip of `main` would also block the repair of a cancelled run). The create-release endpoint refuses the built-in token when the target commit changes a workflow file relative to the default branch; what that means for a target that `main` has moved past is not documented. The opening's first run tests neither. Both are very unlikely.
- **What the release check takes on trust** until the opening shows it: that `gh` is on the hosted runner; that `Release` starts for the Gates run of the very push that adds `release.yml`; that `git ls-remote` with the built-in token as a per-command header works on a private repository with `persist-credentials: false`, and that `::add-mask::` hides the encoded value; the JSON field names of `gh run list` and `gh release view` used in step 5; and that the tag `gh release create` makes shows the commit's id in `git ls-remote`.
- **A package build.** setuptools is not installed where this plan runs and nothing is installed, so no task builds the package; the hosted install step and the release job's `python -m build` are the first builds. Task RI's edit to `pyproject.toml` is checked by parsing it, not by building.
- **A failed release after the tag exists.** The workflow ends green without a release when the tag exists, so a run that created the tag and then failed cannot be retried by the workflow; it is a wait for the owner.
- **Platform line endings of the checkout.** The first plan's byte tests write files with `\n`; whether a Windows checkout changes the line endings of tracked files is first seen in the hosted run.
