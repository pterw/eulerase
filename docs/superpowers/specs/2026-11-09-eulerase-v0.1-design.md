# Eulerase v0.1: design

Status: the scope and design were approved by the owner on 2026-11-09; this written version awaits the owner's review. Once
reviewed, it is the authority for the v0.1 implementation plan: where the plan and this document disagree, this document
wins until it is changed in a commit of its own.

## 1. Purpose

Eulerase is a desktop and command-line tool for learning and exploring de Bruijn graphs. Given sequences and a k, it:

1. builds the de Bruijn graph (nodes are (k-1)-mers, edges are k-mers);
2. finds a minimum set of Eulerian trails that uses every edge once, and lets the user step through the walk;
3. assembles contigs from the graph, with every simplification visible and chosen by the user.

It is for students, teachers and bench biologists working with short sequences: a few reads typed by hand, a gene, a plasmid,
a phage or a mitochondrial genome. It is not a production assembler.

### 1.1 The boundary

Eulerase shows what is in the sequences it is given and, once the comparison design is built (section 10), differences
between them. It never reads genotype files, never
looks up variant identifiers, and never interprets a result for a person. That work belongs to Lucidase, a separate
project.

### 1.2 The promise

Everything Eulerase shows is computed, named for what it is, and tested against an independent answer. A feature that cannot
meet that standard is parked until it can (section 3).

Three claims are kept apart, in the code, the labels and the README:

1. A trail is correct for the graph: it uses each edge once and spells a string whose k-mers are those edges.
2. A contig is a valid path in the assembly graph built from the k-mers given.
3. A sequence exists in an organism.

Eulerase makes the first two and never the third. A contig is not a validated assembly.

## 2. Origin

Eulerase starts as a fresh copy of the de Bruijn explorer that lived inside the Lucidase repository (commit `951e048`,
directory `debruijn/`, plus the explorer half of a shared Tk window). The explorer descends from a single-file prototype whose
citrus palette the tool keeps.

No git history is carried over. Nothing concerned with genotype files, variant annotation or clinical reports is copied,
not even in a first commit that a later one removes.

Eulerase imports nothing from Lucidase and needs none of its files. A fresh clone with only its pinned dependencies
installed passes the unit tests, and CI runs them that way.

The explorer was audited on 2026-11-09 before this design was written: four read-only passes (graph and assembly, sequence
and statistics helpers, tests, launcher and GUI), then an independent check that re-ran nine selected findings from their
descriptions alone. Section 4 lists the findings v0.1 must fix, under the identifiers (A1, B2 and so on) that this document and the tests use.
Commit messages describe a defect in words and carry no identifier.
Findings about parked or dropped features are summarised in section 3 by their reason.

is repaired (section 12).

### 5.1 Two graphs, and what a count means

Eulerase keeps two views of the same k-mers. Each has its own contract. The source already works this way; v0.1 names it
and tests it.

| | Walk graph | Assembly graph |
|---|---|---|
| An edge is | one occurrence of a k-mer in the input | one distinct k-mer |
| A k-mer seen n times is | n parallel edges | one edge with multiplicity n |
| Used for | the Eulerian trail cover and the step-through | contigs, metrics, the k-mer spectrum, GFA |
| Contract | every occurrence is used exactly once across the cover; a trail spells a string whose k-mers are exactly its edges, in order | every distinct k-mer left in the graph after any filter lies in exactly one contig (with both strands, one contig of each reverse-complement pair is reported, so a k-mer or its reverse complement does); a contig's sequence is never lengthened because its k-mers were seen more than once |

"Treat as a set" drops repeated occurrences before either graph is built, so the walk graph then has one edge per distinct
k-mer too.

With both strands, a multiplicity counts occurrences in the input and in its reverse complement. A k-mer that is its own
reverse complement (`ATGCAT`, for example) is therefore counted twice for each occurrence, because it occurs in the
sequence and again in its reverse complement; the independent count in the tests does the same.

Two cases fix the meaning, and both are tests:

- **A read given ten times.** `ATGC` ten times at k=3: the walk graph has 20 edges and its minimum cover is ten trails, each
  spelling `ATGC`. The assembly graph has two edges of multiplicity 10 and one contig, `ATGC`. As a set: one trail.
- **A repeat inside one sequence.** `ATGCATGCATGC` at k=3: the walk graph has 10 edges (`ATG` and `TGC` three times, `GCA`
  and `CAT` twice) and one trail that spells the input. The assembly graph is a four-edge cycle with mean multiplicity 2.5,
  and its one contig, `ATGC`, is marked as a cycle and is shorter than the input: it is the circle of four letters, written once.

**A cycle contig is the circle, written once.** An isolated cycle of n distinct k-mers gives a contig of exactly n
letters: the first letter of each k-mer in cycle order, rotated to the least rotation of that circle. n can be smaller
than k-1 (`AAAAAAAA` at k=3 is `A`, length 1). Its length and edges are n, its GC is over the n letters, and the total
length, N50, L50 and N90 use n. With both strands, of a cycle and its reverse-complement twin the one whose least
rotation is smaller is reported. What a user reads says `cycle` (the Contigs table column, the metrics line), and one
note appears when at least one contig is a cycle: "A contig marked as a cycle is a closed path in the graph: it can be a
circular molecule or a repeat, and its position 1 is its alphabetically first rotation, not a biological start."

**The mean multiplicity of the assembly** is the sum of the contigs' k-mer counts over the sum of their edges, labelled
`mean multiplicity`.

**Multiplicity is not depth.** The number attached to a k-mer is how many times it occurs in the input, and nothing more.
Ten reads of one molecule and one sequence with a tenfold repeat give the same number, and Eulerase cannot tell which it was
given. So:

- labels, table headers, option names and exports say "multiplicity" or "times seen", never "coverage" or "depth";
- no output presents a multiplicity as read depth, copy number or any other biological quantity;
- the minimum-multiplicity setting and tip clipping are described as filters on occurrence counts. Their help text says they
  act as error filters only when the input is a set of reads, and that on a single assembled sequence a low count marks a
  rarer k-mer, not an error.

In sections 4 and 8.3 the words "coverage" and "30x" describe test inputs that are simulated reads, where the term is correct.

## 6. Behaviour

### 6.1 Input

- Sequences are typed, pasted, or loaded from a file. A k-mer list is a second input mode.
- Any alphabet builds a graph, so `LEMONLEMONADE` stays the first example. Features that need DNA (both strands, GC, ORFs)
  are offered only when every letter of the non-empty records is A, C, G, T or N, and say "not available" otherwise, with one
  note: "GC and ORFs are not available because the input holds letters other than A, C, G, T and N: <letters>." (the
  distinct letters, sorted, comma separated). An input whose every record is empty is refused with "Every record is empty;
  give a sequence with letters."
- The line endings `\r\n` and a lone `\r` are read as `\n` before anything else reads the text.
- An N is a letter like any other in the graph. No base is invented for it. Two unknown bases therefore look the same to
  the graph, and a contig that contains N is marked.
- k is a whole number of at least 2. That rule lives in one place and every entry point uses it.

### 6.2 Simplification

- Default: none. The graph and contigs reflect exactly the k-mers given.
- Minimum multiplicity: the user picks a value while looking at the k-mer spectrum. Distinct k-mers seen fewer times are
  removed from the assembly graph, and the result says how many. The walk graph is never filtered.
- Tip clipping: a separate switch on the assembly graph, as A2 requires. Minimum multiplicity is applied first, then tip
  clipping. The result says how many distinct k-mers and how many branches were removed. Tip clipping removes dead ends,
  not bubbles; for reads, a minimum multiplicity is what removes most error k-mers.
- Each result records the settings that produced it. FASTA descriptions, the GFA header line, the GenBank comment and the
  figure title carry them; CSV files do not. The status bar and the Assembly tab show them.

### 6.3 Determinism

Computation and rendering carry different promises, and the first is never weakened to fit the second.

- **Results.** The same input and settings give the same trails, contigs, numbers and ordering, on every run and on every
  supported platform (Windows and Linux), with the pinned versions of the dependencies.
- **Text outputs** (FASTA, GFA, GenBank, CSV, and what the command line prints) are byte-identical across runs and supported
  platforms for the pinned versions. That needs, and v0.1 defines once each: a fixed order of records and rows; one number
  format (whole numbers as integers, ratios to a fixed number of decimals); UTF-8 with `\n` line endings written
  explicitly and no byte-order mark; and no value taken from the clock, the host or a file path. Where a format requires a
  date, the writer sets a fixed one itself, not a library default, and the README says so. A byte-level test of each
  writer runs on both platforms.
- **Layout.** Node coordinates are identical across runs and hash seeds for one platform and one set of pinned versions.
  Across platforms they are equal within a tolerance the test states, because the layout is floating-point arithmetic.
  Across library versions nothing is promised: the pinned versions are the contract.
- **Figures.** What a figure shows (which nodes and edges, their labels, colours and coordinates) is reproducible and is what
  the tests compare. The bytes of an image file are not promised across platforms, since fonts, backends and file metadata
  differ. An image-byte comparison may be used only inside one pinned environment, and is never a gate.

### 6.4 Limits

Three named limits: the k-mer limit (the largest number of k-mers accepted), the drawing limit and the table row limit
(the most table rows shown). The k-mer limit is 300,000 (its starting value, the explorer's 500,000, was lowered by
measuring build time) and the table row limit is 2,000. The drawing limit is one limit with two counts: 400 nodes, or a
number of arrows set by measurement (walk-graph edges drawn, self-loops and parallel edges included). Above the k-mer
limit, the input is refused before any work, with the limit in the message; with both strands, both strands' k-mers
count. Above either count of the drawing limit, the tables are shown and the figure says why it is empty and which count
was over. A table that is cut says how many rows it shows of how many, and an export always carries every row. A build at
the k-mer limit finishes within 30 seconds on the development machine (22 to 26 s with tip clipping at k=11), and the
measurement is recorded.

### 6.5 Errors

A failure the user can cause is one sentence that says what was wrong and what to do. It is never a traceback and never a
library's own multi-line text. On the command line it goes to stderr with a non-zero exit code. Nothing is caught and
ignored: a contig or record that cannot be processed is counted and reported.

### 6.6 Command line

`eulerase` with no arguments opens the window, so a double-clicked executable does the expected thing. With input it prints
results and writes the requested files. `--gui` with input opens the window with that input loaded.

Input: `--seq`, `--kmers`, `--file`. Settings: `-k`, `--both-strands`, `--unique`, `--min-count N`, `--clip-tips`.
Output: `--figure`, `--csv`, `--gfa`, `--contigs`, `--genbank`, `--metrics`. The plan fixes the exact spellings and help
text. `--file` reads any supported format. `--csv` takes a prefix and writes one file per table. The exit code is 0 on success,
1 when an input or an output failed, and 2 when the options were wrong. Options given without an input, two inputs together, and `-k` with `--kmers`
are errors (D8).

### 6.7 What the written files hold

- **FASTA.** A cycle's record holds its n letters, and its description gains `circular=true` right after
  `orfs=<count>`. Other contigs are unchanged.
- **GFA.** A cycle's segment holds its n letters (`LN:i:<n>`) and has one self-link, `L ctg<a> + ctg<a> + 0M` (a is the contig's number), and no
  other link. Every other contig is linked by the (k-1)-letter overlap, including to itself when its last k-1 letters
  equal its first k-1.
- **GenBank**, a file for viewers, not for submission. A cycle's record holds its n letters with topology circular, and
  its COMMENT gains the line "Topology: a cycle in the assembly graph; it can be a circular molecule or a repeat." An ORF
  that crosses position 1 is a joined location in transcript order: `join(a..n,1..b)` on the plus strand,
  `complement(join(a..n,1..b))` on the minus strand. No `/frame` is written; the frame goes in the CDS `/note` (for
  example `/note="frame +2"`). Every record has one `source` feature spanning it, with `/mol_type="other DNA"` and
  `/note="assembled by Eulerase from the input; organism not known"`. No `/organism` is written (section 1.2), and no
  `/transl_table`, which INSDC asks for only when the code is not the universal one.

## 7. The window

Tk stays: it comes with Python's own installers on Windows and macOS and needs no extra dependency.

- **Layout.** Input and settings on the left. The graph in the centre, with the step controls under it. Tables in tabs
  below: Edges, Nodes, Trails, Contigs, Assembly. A status bar along the bottom carries messages and the busy state.
- **Menus.** Exports live in a File menu, each with a keyboard shortcut. The row of export buttons goes.
- **Assembly tab.** The k-mer spectrum is drawn as a chart with the minimum-multiplicity setting marked on it, next to the
  metrics. This is where a learner sees what a cutoff does.
- **Threads.** Only the window's own thread touches a widget. A build runs in a worker that returns its result through a
  queue the window polls. A running build can be abandoned with a Stop control: its result is discarded when it arrives, and the window shows
  no result. Starting a new build abandons the one in progress. After a failed or abandoned build nothing from an earlier
  build remains on screen or can be exported.
- **Size.** The default window fits a 1366x768 screen. Nothing needed is cut off at the minimum size. The legend sits
  outside the plot area and never covers the title.
- **Text.** No glyph outside the Basic Multilingual Plane. Labels are sentence case.
- **Palette.** The citrus palette of the prototype, defined once.
- **Examples.** The explorer's nine sequence examples, minus any that only demonstrated a parked feature. An example may set its own k and
  settings.

A comparison view arrives with the comparison design (section 10). v0.1 leaves room for it as a top-level tab and builds
nothing for it.

## 8. Tests

### 8.1 Rules

- A test names the behaviour it guards and fails if that behaviour breaks. It checks an intended result against an
  independent answer, never the code against itself.
- One test per behaviour. Near-duplicates become one parametrized test. No test pins wording or a constant.
- No test needs a display, the network, or the user's home directory.
- A wrong green is worse than a red.

### 8.2 Oracles

- k-mer and graph construction against a brute-force count.
- A trail cover against the edge multiset, contiguity, and the minimum number of trails: for each weakly connected
  component, the larger of 1 and the sum of the positive node balances (out-degree minus in-degree), summed over components.
- Contigs against a known genome with no repeated (k-1)-mer: each is a substring of it or of its reverse complement. With
  repeats that need not hold; a contig is then checked as a valid path in the assembly graph (section 1.2); a cycle is read around its circle.
- Metrics against values computed directly from the contigs.
- GFA, FASTA and GenBank by reading the written file back with a parser that shares no code with the writer.
- The ORF finder against a six-frame translation, and, for a cycle, against a read around the circle.
- The two graphs of section 5.1 against its two worked cases, and against a brute-force count of occurrences and of distinct
  k-mers on random input: repeated reads, a repeat inside one sequence, and the same input as a set.

Every oracle is shown once to catch a wrong answer, so a pass means something.

### 8.3 Truth tests a parked feature must pass to return

- Error model: on error-free reads it suggests no cutoff. On reads with errors, the suggested cutoff removes nearly all error
  k-mers and almost no genome k-mers, across coverage from 10x to 60x. The design that brings the feature back fixes both
  thresholds before measuring, no looser than 95% and 1%. On a k-mer spectrum with a single peak it says it found no error peak.
- Binning: contigs from two synthetic genomes are separated the same way whatever their orientation, and contigs from one
  genome are never split.

### 8.4 Starting point

The audit kept 25 of the explorer's 43 test functions after merging duplicates and cutting tests that pinned wording. It
found five that pass with the behaviour broken (three figure tests that pass with invisible nodes, a file-loading test
that passes when sequences are dropped, and a test of a parked feature) and several behaviours with no test: tip clipping,
the ORF finder's output, the k-mer spectrum, the FASTA, GenBank and CSV exports, and nearly every error path (only k below 2 and the k-mer limit are
tested). v0.1 starts from the 17 keepers that guard kept features (the other 8 guard the reference comparison and binning,
which are parked), repairs the weak ones among them, and fills those gaps.

## 9. The repository

- **Licence:** MIT. The tool ships no third-party data, and its dependencies are permissively licensed.
- **README:** what the tool is, a screenshot, install and run, the examples, the limits in section 6.4, and what it does
  not do (section 1.1). It describes only shipped behaviour.
- **AGENTS.md:** the engineering rules: document roles; setup; gates; commit
  rules; test rules (section 8.1); an anti-pattern list seeded from section 4; the rules of section 12.1 for
  any agent or model that picks work up; and the invariants below.
- **Invariants:**
  1. Every number shown has a test against an independent oracle.
  2. Nothing is removed from the user's data unless the user asked, and the result says what was removed.
  3. A label says what was computed, in plain words.
  4. The same input gives the same output.
  5. A failure is a message. A failed step leaves no stale result behind.
  6. The core imports neither the GUI nor the plotting library.
  7. k-mers from one sequence are not independent observations. No statistic treats them as replicates, and no result is
     shown for a design that cannot support it.
  8. A multiplicity is a count of occurrences in the input. It is never shown as depth, copy number or evidence of anything
     in an organism (section 5.1).
  9. A parked feature returns only by passing its truth tests (section 8.3) and a change to this document. Being easy to
     build is not a reason. No dependency or abstraction is added that a shipped behaviour does not need.
  10. A wrong green is worse than a red: a test or gate that passes while the behaviour is broken is a defect of its own.
- **Gates:** the unit tests and a linter, on Windows and Linux, in CI and before a commit.
- **Package release:** version 0.1.0 is released as a source distribution and a wheel attached to a GitHub release, under
  the tag `v0.1.0`. A release workflow makes a release when a change merged into `main` carries a version that has no tag
  yet, and only from a commit whose gates ran green on both systems; a merge that does not change the version releases
  nothing. Nothing is uploaded to a package index in v0.1. The executable and the release report below are a later step
  and are not part of the package release.
- **Executable:** a Windows build is a later step of v0.1, after the package release. Its size and start-up time are
  measured and recorded in the README. The window gets a hands-on pass before the executable is built, covering its real
  geometry and responsiveness.
- **Release report:** `docs/v0.1-report.md` states what was built, the tests that were run and their results, the limits,
  the executable's measurements, and every finding left open. It says "not checked" for anything that was not.
- **Opening the repository:** it stays local until the code and tests have been carried over and checked and the
  window is built (section 12, steps 1 to 6). It is then opened, public, with what a reader and a contributor
  need on the first day: the README; CI workflows that run the gates on every push to `main` and on every pull request,
  except a pull request that changes only files on a short, fixed list of documentation paths (Markdown under `docs/`,
  `CONTRIBUTING.md` and the issue and pull request templates; the README and `AGENTS.md` are not on it), modelled on the
  author's other
  repositories; the release workflow; a pull request template; issue templates; `CONTRIBUTING.md`; a changelog; a short
  security policy; and `AGENTS.md`. Automated dependency
  updates and a scheduled CI run are decided at that point, and added only if they earn their keep. Nothing a public
  repository could not hold is ever committed: no personal paths, no personal data.

## 10. Later designs

These are not part of v0.1. They are recorded so v0.1 does not close a door.

- **Comparison and trees.** A separate comparative sequence-divergence project, planned to join later, supplies the kernel: sample identity,
  canonical k-mer counts, shared and private k-mers, and its synthetic truth cases. It joins on the one graph core in
  section 5; colour is a per-sample count on an edge, not a second graph. Its own trail and unitig code is not carried
  without passing the oracles in section 8.2. It is meant to serve any comparison of sequences and the building of trees
  from them. Trees are distance-based and alignment-free, and are labelled as such. The distance definition is taken from a published source named in that design. No tree is drawn when too few k-mers are shared, and no support value is derived from
  resampled k-mers (invariant 7). The tree code is tested on sequences simulated along a known tree.
- **A germline and somatic worked example.** A synthetic sequence with segments that its processed copy has lost, including
  one case with a short repeat at the cut points. The comparison design keeps private paths, shared paths and the k-mers
  that span a rearrangement junction as separate things, and does not assume that an eliminated segment always produces
  one particular shape in the graph. Testing a hypothesis about evolutionary rates is a non-goal: it needs alignments and
  substitution models.
- **Selectable genetic codes** for the ORF finder, including NCBI translation table 6 for ciliate nuclear genes. v0.1 uses
  the standard code only and says so in its output.
- **Preregistered inference and reports** from the divergence project, as a command-line feature, after the comparison
  layer is proven.
- **A small-genome workbench**, which is where the parked error model and binning would earn their return.
- **A package index.** v0.1 is released as a tagged GitHub release that holds a source distribution and a wheel, and
  nothing is uploaded to a package index. Publishing each release to the Python Package Index is the next milestone
  after the opening: it adds one publishing step to the release workflow and changes nothing in the tool.
- **A three-dimensional view of a polymer chain.** Recorded as a candidate, with no design yet. Its design starts from
  the claim the picture makes. An ORF that the tool reports is an open reading frame, not a verified protein
  (section 1.2), so the view never shows a fold for one as if it were known: it shows either a structure that is
  already published for a sequence the user names, with its source, or a schematic that is labelled as a schematic.
  It is a separate feature with its own truth tests (section 8.3), and it does not enter the graph core.

## 12. Order of work and evidence

The plan follows this order. The core's contracts and oracles come before any window work.

1. **Scaffold.** Package layout, licence, gates and CI, with one trivial test, so every later step lands through the gates.
2. **Carry the core.** Bring the verified graph, trail, assembly, layout, figure, ORF, file-reading and file-writing code into the modules of
   section 5, with the
   oracle tests of section 8.2 written first and passing against the carried code. The parked and dropped code (error
   model, binning, reference comparison, molecular weight) is not carried: in the source the core imports it and calls it
   on every build, so those calls are cut as the code is carried, and nothing else is changed in this step.
3. **Repair.** One finding from section 4 at a time, in a commit of its own, as targeted repair and not a rewrite. How a
   repair is proven depends on where the defect lives:
   - **In carried code** (A2, A4, A5, A8, B2, B6, B7, B9, R1, R2, R3): step 2 commits the test as an expected failure that names the
     finding. The repair is the smallest change that makes it pass, and removes the marker.
   - **In code that is left behind or rebuilt** (A1, D2, D3, D8, D10, D12): the defect cannot be red here, because its
     code never arrives. The new test is run once against the source at its original commit and must fail there; the
     command and its output go in the task's report. It then passes here. The repairs of the command-line findings (D2, D3,
     D8) come after step 4, because their code is the command line.
   - **In the window** (D4 to D7, D9, G1, the layout): presenter tests written before the presenter, and the hands-on pass.
   - A3 is a review item (section 4).
4. **Command line.**
5. **Presenter**, tested without a display.
6. **Window.**
7. **README and AGENTS.md.**
8. **Hands-on pass, executable and release report.**

For every step the plan states the expected behaviour and how it is verified. Each task's report tells tests that were run
(with their output) apart from tests that were only planned. A departure from this document is made by changing this
document in its own commit, with the reason.

### 12.1 For any agent or model that picks this up

The plans are written for one workflow (one writer per task, a separate reader, one controller that lands), but another
tool can execute them if it keeps these rules:

- **One task, one commit**, or the commits its steps name. Never gather several tasks into one commit: a change that
  cannot be rolled back or reviewed alone is a defect of process.
- **Lean tests** (section 8.1). Write the tests a task names. Add one only where an intended behaviour would otherwise
  have no test, and say so. More tests are not more safety: a test that pins wording, repeats another, or checks the code
  against itself is removed.
- **An unclear instruction is not a conflict.** Resolve it from the section of this document the task cites, say in the
  task's report which reading you took and why, and carry on. Stop and ask only for a real contradiction between two
  rules, or where the choice would change a number, a label or a file format a user sees.
- **Carry, then repair.** The verified code is moved as it is; each defect is repaired in its own step with its failing
  test first. Do not rewrite what works.
- **Say what was run.** A report lists the commands that were run with their output, and separately what was not run.
