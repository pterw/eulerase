# Eulerase v0.1: design

Status: the scope and design were approved by the owner on 2026-11-09; this written version awaits the owner's review. Once
reviewed, it is the authority for the v0.1 implementation plan: where the plan and this document disagree, this document
wins until it is changed in a commit of its own.

## 1. Purpose

Eulerase is a desktop and command-line tool for learning and exploring de Bruijn graphs. Given sequences and a k, it:

1. builds the de Bruijn graph (nodes are (k-1)-mers, edges are k-mers);
2. finds a minimum set of Eulerian trails that uses every edge once, and lets the user step through the walk;
3. assembles contigs from the graph, with every simplification visible and chosen by the user.

It is for students, teachers and bench biologists working with short sequences: a few reads typed by hand, a gene, a plasmid,
a phage or a mitochondrial genome. It is not a production assembler.

### 1.1 The boundary

Eulerase shows what is in the sequences it is given, and differences between them. It never reads genotype files, never
looks up variant identifiers, and never interprets a result for a person. That work belongs to Lucidase, a separate
project.

### 1.2 The promise

Everything Eulerase shows is computed, named for what it is, and tested against an independent answer. A feature that cannot
meet that standard is parked until it can (section 3).

## 2. Origin

Eulerase starts as a fresh copy of the de Bruijn explorer that lived inside the Lucidase repository (commit `951e048`,
directory `debruijn/`, plus the explorer half of a shared Tk window). Both descend from a single-file prototype,
`debruijn_lemon.py`, whose citrus palette the tool keeps.

No git history is carried over. Nothing concerned with genotype files, variant annotation or clinical reports is copied,
not even in a first commit that a later one removes.

The explorer was audited on 2026-11-09 before this design was written: four read-only passes (graph and assembly, sequence
and statistics helpers, tests, launcher and GUI), then an independent check that re-ran the nine most serious findings from
their descriptions alone. Section 4 is the public record of that audit. Its identifiers (A1, B2 and so on) are used
throughout.

## 4. Findings v0.1 must fix

Each row is a defect confirmed in the source code, the behaviour v0.1 must have, and how that is checked. "Confirmed twice"
means the independent check reproduced it with its own inputs.

| ID | Defect in the source | Required behaviour | Check |
|---|---|---|---|
| A1 | An automatic coverage cutoff runs on every build. On error-free reads tiled over a random 1,000-base genome it returned an 850-base contig; on 5,000 bases at 30x and 60x it lost 13 to 80 bases per end, and with randomly placed reads it split the genome into 4 to 19 contigs. No option turned it off. Confirmed twice | No k-mer is removed unless the user sets a minimum coverage. The default is none. When one is set, the result states how many k-mers were removed | Error-free reads covering a random genome with no repeated (k-1)-mer give one contig equal to the genome or its reverse complement, with default settings, over several seeds and k |

Each step of the walk redraws the whole figure, about 1.2 s near the drawing limit | Work over about a quarter of a second runs off the window's thread with a visible busy state. ## 5. Structure

One package, `eulerase`. Dependencies point one way: the GUI and the command line depend on the core, and the core depends
on neither. The core never imports Tk or matplotlib.

| Module | Responsibility | Depends on |
|---|---|---|
| `eulerase.sequence` | Normalising input text; alphabet checks; reverse complement; GC | |
| `eulerase.io` | Reading FASTA, FASTQ, GenBank and EMBL, plain or gzip, by content; writing FASTA, GenBank, GFA and CSV | `sequence`, Biopython |
| `eulerase.kmers` | Turning records into k-mers; the one place k is validated; counts | `sequence` |
| `eulerase.graph` | The de Bruijn multigraph; node balance; the Eulerian trail cover; spelling a trail | `kmers`, networkx |
| `eulerase.assembly` | The collapsed graph with coverage; the optional cutoff and tip clipping; contigs; metrics; the k-mer spectrum | `graph` |
| `eulerase.orfs` | The ORF finder | `sequence`, Biopython |
| `eulerase.analysis` | `analyze(...)`: runs the steps above and returns one immutable result | the modules above |
| `eulerase.render` | Layout and the matplotlib figure, usable without a display | `analysis`, matplotlib |
| `eulerase.cli` | The `eulerase` command | `analysis`, `io`, `render` |
| `eulerase.gui.presenter` | The window's state and decisions, with no Tk import, so it is tested without a display | `analysis`, `io` |
| `eulerase.gui.app` | Tk widgets that draw what the presenter says | `presenter`, `render` |

The graph and trail code is carried from the explorer's `graph_core.py` and `assembly.py`, because that is the code the audit
verified. It is re-arranged into the modules above; its algorithms are not rewritten.

## 6. Behaviour

### 6.1 Input

- Sequences are typed, pasted, or loaded from a file. A k-mer list is a second input mode.
- Any alphabet builds a graph, so `LEMONLEMONADE` stays the first example. Features that need DNA (both strands, GC, ORFs)
  are offered only when every letter is A, C, G, T or N, and say "not available" otherwise.
- An N is a letter like any other in the graph. No base is invented for it.
- k is a whole number of at least 2. That rule lives in one place and every entry point uses it.

### 6.2 Simplification

- Default: none. The graph and contigs reflect exactly the k-mers given.
- Minimum coverage: the user picks a value while looking at the k-mer spectrum. k-mers seen fewer times are removed, and the
  result says how many.
- Tip clipping: a separate switch, as A2 requires.
- Each result records the settings that produced it, and every export carries them.

### 6.3 Determinism

The same input and settings give the same trails, contigs, numbers, layout and exported bytes, on any run and platform.
Line endings in written files are `\n`.

### 6.4 Limits

Two named limits, each a single constant: the largest number of k-mers accepted, and the largest number of nodes drawn.
Their starting values are the explorer's (500,000 and 400). Above the first, the input is refused before any work, with the
limit in the message. Above the second, the tables are shown and the figure says why it is empty. The plan measures build
time at the first limit and lowers it if a build cannot finish in a time a user would wait.

### 6.5 Errors

A failure the user can cause is one sentence that says what was wrong and what to do. It is never a traceback and never a
library's own multi-line text. On the command line it goes to stderr with a non-zero exit code. Nothing is caught and
ignored: a contig or record that cannot be processed is counted and reported.

### 6.6 Command line

`eulerase` with no arguments opens the window, so a double-clicked executable does the expected thing. With input it prints
results and writes the requested files. `--gui` with input opens the window with that input loaded.

Input: `--seq`, `--kmers`, `--file`. Settings: `-k`, `--both-strands`, `--unique`, `--min-coverage N`, `--clip-tips`.
Output: `--figure`, `--csv`, `--gfa`, `--contigs`, `--genbank`, `--metrics`. The plan fixes the exact spellings and help
text.

## 7. The window

Tk stays: it ships with Python, needs no extra dependency, and keeps the executable small.

- **Layout.** Input and settings on the left. The graph in the centre, with the step controls under it. Tables in tabs
  below: Edges, Nodes, Trails, Contigs, Assembly. A status bar along the bottom carries messages and the busy state.
- **Menus.** Exports live in a File menu, each with a keyboard shortcut. The row of export buttons goes.
- **Assembly tab.** The k-mer spectrum is drawn as a chart with the minimum-coverage setting marked on it, next to the
  metrics. This is where a learner sees what a cutoff does.
- **Size.** The default window fits a 1366x768 screen. Nothing needed is cut off at the minimum size. The legend sits
  outside the plot area and never covers the title.
- **Text.** No glyph outside the Basic Multilingual Plane. Labels are sentence case.
- **Palette.** The citrus palette of the prototype, defined once.
- **Examples.** The explorer's nine sequence examples, minus any that only demonstrated a parked feature.

A comparison view arrives with the comparison design (section 10). v0.1 leaves room for it as a top-level tab and builds
nothing for it.

## 8. Tests

### 8.1 Rules

- A test names the behaviour it guards and fails if that behaviour breaks. It checks an intended result against an
  independent answer, never the code against itself.
- One test per behaviour. Near-duplicates become one parametrized test. No test pins wording or a constant.
- No test needs a display, the network, or the user's home directory.
- A wrong green is worse than a red.

### 8.2 Oracles

- k-mer and graph construction against a brute-force count.
- A trail cover against the edge multiset, contiguity, and the minimum number of trails (per connected component, the larger
  of 1 and the sum of positive node balances).
- Contigs against a known genome: each is a substring of it or of its reverse complement.
- Metrics against values computed directly from the contigs.
- GFA, FASTA and GenBank by reading the written file back with a parser that shares no code with the writer.
- The ORF finder against a six-frame translation.

Every oracle is shown once to catch a wrong answer, so a pass means something.

### 8.3 Truth tests a parked feature must pass to return

- Error model: on error-free reads it suggests no cutoff. On reads with errors, the suggested cutoff removes error k-mers
  and no genome k-mer, across coverage from 10x to 60x. On a single coverage peak it says it found no error peak.
- Binning: contigs from two synthetic genomes are separated the same way whatever their orientation, and contigs from one
  genome are never split.

### 8.4 Starting point

The audit kept 25 of the explorer's 43 test functions after merging duplicates and cutting tests that pinned wording. It
found five that pass with the behaviour broken (three figure tests that pass with invisible nodes, a file-loading test
that passes when sequences are dropped, and a test of a parked feature) and several behaviours with no test: tip clipping,
the ORF finder's output, the k-mer spectrum, the FASTA, GenBank and CSV exports, and every error path. v0.1 starts from the
keepers, repairs the weak ones that guard kept features, and fills those gaps.

## 9. The repository

- **Licence:** MIT. The tool ships no third-party data, and its dependencies are permissively licensed.
- **README:** what the tool is, a screenshot, install and run, the examples, the limits in section 6.4, and what it does
  not do (section 1.1). It describes only shipped behaviour.
- **AGENTS.md:** the engineering rules, following the owner's other repositories: document roles; setup; gates; commit
  rules; test rules (section 8.1); an anti-pattern list seeded from section 4; and the invariants below.
- **Invariants:**
  1. Every number shown has a test against an independent oracle.
  2. Nothing is removed from the user's data unless the user asked, and the result says what was removed.
  3. A label says what was computed, in plain words.
  4. The same input gives the same output.
  5. A failure is a message. A failed step leaves no stale result behind.
  6. The core imports neither the GUI nor the plotting library.
  7. k-mers from one sequence are not independent observations. No statistic treats them as replicates, and no result is
     shown for a design that cannot support it.
- **Gates:** the unit tests and a linter, on Windows and Linux, in CI and before a commit.
- **Executable:** a Windows build is the release step for v0.1. Its size and start-up time are measured and recorded in the
  README. The window gets a hands-on pass before the release.
- **Publishing:** the repository stays local until the owner approves a search for other projects named Eulerase and
  gives the word to publish. Nothing a public repository could not hold is ever committed: no personal paths, no
  personal data.

## 10. Later designs

These are not part of v0.1. They are recorded so v0.1 does not close a door.

- **Comparison and trees.** The owner's comparative sequence divergence project supplies the kernel: sample identity,
  canonical k-mer counts, shared and private k-mers, and its synthetic truth cases. It joins on the one graph core in
  section 5; colour is a per-sample count on an edge, not a second graph. Its own trail and unitig code is not carried
  without passing the oracles in section 8.2. Owner ruling: it "should be useful for any comparison and tree
  construction". Trees are distance-based and alignment-free, and are labelled as such. The distance definition is taken
  from its published source. No tree is drawn when too few k-mers are shared, and no support value is derived from
  resampled k-mers (invariant 7). The tree code is tested on sequences simulated along a known tree.
- **A germline and somatic worked example.** A synthetic sequence with segments that its processed copy has lost, including
  one case with a short repeat at the cut points, to show eliminated segments as private paths in a coloured graph. Testing
  a hypothesis about evolutionary rates is a non-goal: it needs alignments and substitution models.
- **Preregistered inference and reports** from the divergence project, as a command-line feature, after the comparison
  layer is proven.
- **A small-genome workbench**, which is where the parked error model and binning would earn their return.
